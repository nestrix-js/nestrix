# @nestrix-js/ui

## 0.1.0-alpha.2

### Patch Changes

- d64c251: Standalone server: browser sign-in works again. The login page's `no-referrer` policy made browsers send `Origin: null` with the form, which the origin check refused, so every browser sign-in got 403. Pages now use `Referrer-Policy: same-origin`, and a missing or `null` Origin is accepted only with `Sec-Fetch-Site: same-origin`; cross-site and same-site requests stay refused. A Playwright test now submits the real login form.

## 0.1.0-alpha.1

### Patch Changes

- e2f0a14: Nestrix's own resource now carries a random `service.instance.id` per process, so replicas of one service can be told apart in the standalone server. Set the attribute yourself with `resourceAttributes` or `OTEL_RESOURCE_ATTRIBUTES` to override it.

## 0.1.0-alpha.0

### Minor Changes

- b626440: 1.0 API review (D-69). Renames and removals, before anything is published:
  
  - `ignore.routes` is now `ignore.paths` (it matches literal request paths, not route templates).
  - `methods.enabled` is gone: `methods: false` turns method spans off.
  - The types `NestrixMethodOptions` and `NestrixIntegrationOptions` are now `NestrixMethodsOptions` and `NestrixIntegrationsOptions`.
  - `SpanOptions` is no longer re-exported; import it from `@opentelemetry/api`.
  - `logs.export` follows the metrics rule: it starts only when Nestrix owns the trace provider and trace export is on. A host-owned SDK gets no Nestrix `LoggerProvider` (one log line says so), and `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` alone no longer turns it on.
  - Fixed: exported metrics carried no `service.version`.
  - `user` and `authorize` accept a callback with a typed request parameter; `RedactHook` may return `void`.
  - Internal to the bundled UI: `SpanRecord.service`, a required `MetaResponse.mode`, and `statistics.windowsMinutes` renamed `windowMinutesOptions`.
- decbfa6: App map API. The dashboard serves `GET api/v1/map?windowMinutes=15|60`: the app and what it calls (databases, caches, HTTP hosts, queues), with calls, errors, p50 and p95 per target, built from the sampled traces in the in-memory store. At most 200 nodes; targets past that fold into one `other` node.
- 5d9ef74: Document BullMQ background jobs: setup with `bullmq-otel` and the trace shape (the job's processing is a child of the enqueue span).
- 6c7585e: Class statistics. While the dashboard is on, calls reported by level 2 method wrappers are counted before sampling per class and method (calls, errors, total and largest duration, bounded at 500 classes by 50 methods), and `GET /_nestrix/api/v1/classes?windowMinutes=15|60` returns the window sums plus an own-time estimate per method taken from the sampled spans in the store.
- 5fc299f: Dashboard: a Classes view (per-class calls, errors, average, total and estimated own time, expandable to methods, sortable, 15 or 60 minute window, with the `main.ts` line shown when method spans are off) and a Map view (the app in the centre and what it calls, edges labelled with calls, p95 and error rate and coloured by error rate, with the same edges in a table below).
- 23fcc98: On-demand CPU profiler in the embedded dashboard (D-70). A new Profiler tab starts a capture of 1 to 120 seconds (default 30) with `v8.startCpuProfile`, one at a time per process, and shows a flame graph, the top functions by self time and a `.cpuprofile` download; the last three captures are kept in memory. Nothing is loaded or running between captures. Starting a capture briefly pauses the app (about 10 ms per MB of compiled code); the dashboard shows the last measured pause before you start.
  
  New option `ui.profiler` (default `true`): the profiler is offered only where the dashboard is authenticated (`enabled: true` with `auth`, or `'auto'` with the startup token or `auth`); `false` removes it and its routes. Starting a capture is the dashboard's first state-changing request: besides dashboard access it requires `Sec-Fetch-Site: same-origin`, an `Origin` equal to the server's own origin, a JSON body and a `Content-Length` of at most 1 KB. Behind a reverse proxy, pass the original `Host` header. `meta` gains `profiler: { available, running }`.
- 9434a2d: Database and cache spans (level 3), with no setup and no Node flags. `pg` queries are traced whenever `pg` is installed (`integrations.pg: false` turns it off): client and pool, promise, callback, `pg-cursor` and `pg-query-stream`, including a nested `pg` copy an ORM such as MikroORM loaded at import time or in a provider factory (a copy first loaded during a request is not traced). A span covers the query only, not the wait for a pool connection, and lands in the trace of the request that issued it even when the pool is contended; a pool that cannot connect records an error span. `mysql2` (`integrations.mysql2: true`) and `ioredis` (`integrations.ioredis: true`) are opt-in, because once anything subscribes to their tracing channels mysql2 swallows an error from an event-emitter query with no `'error'` listener and ioredis swallows the rejection of a failing command nobody awaits, where either would otherwise crash the process. Redis commands that run outside any trace (connection handshakes, commands queued before the connection was ready) produce no span unless `integrations.ioredis.rootSpans` is `true`. Spans follow the current OpenTelemetry database conventions (`db.system.name`, `db.query.text`, `db.operation.name`, `db.namespace`, `server.address`, `server.port`). Statements are recorded with every literal replaced by `?`, comments removed and `IN (…)` lists collapsed, capped at 2,048 characters; a statement that cannot be parsed safely is replaced by a fixed placeholder text. For Redis only the command and its key are recorded. Bind parameters and values are never recorded.
- be61ad9: Embedded dashboard. With `@nestrix-js/ui` installed (an optional peer of `@nestrix-js/nestjs`, same version), `NestrixModule` serves a read-only dashboard at `/_nestrix` from inside the application, on Express, Fastify and platform-node: recent traces, one trace's spans, errors, and per-route statistics counted before sampling. Routes sit outside the global prefix and versioning and are registered with the adapter's own `get` in `onModuleInit`; every response is written to the raw response with the dashboard's own Content-Security-Policy and no CORS headers, whatever the host's CORS configuration. By default (`ui: 'auto'`) it is served only when `NODE_ENV` is `development` or unset, to loopback requests without forwarding headers that carry the startup token: open the link Nestrix logs once the application listens. `ui: { enabled: true, auth }` serves it in any environment behind a token or a custom `authorize(request)`. Dashboard requests are not traced, and a host route that shadows the dashboard is logged once. `ui.startupToken: false` opts out of the startup token (a same-host reverse proxy then exposes the dashboard when `NODE_ENV` is unset). A host that owns its OpenTelemetry SDK adds `nestrixSpanProcessor()` to its `spanProcessors` to feed the dashboard. The new `store` option (`maxTraces`, `maxBytes`) bounds the in-memory store, oldest trace evicted first. Route statistics are counted before sampling, and the error list holds spans with error status (5xx; a thrown 4xx is not an error).
- 86d470c: Headless tracing: `NestrixModule.forRoot()` and `forRootAsync()`, option resolution with `OTEL_*` and `NESTRIX_ENABLED` environment variables, and Nestrix's internal diagnostics.
- 2d69468: HTTP server spans on Express, Fastify and platform-node, named by route template, with handler attribution (`code.function.name`), exceptions thrown by handlers and pipes, client-abort marking (`nestrix.http.aborted`), header allowlists and query redaction. Process-level errors are observed through `uncaughtExceptionMonitor` only.
- 0f55f44: Log correlation. `NestrixLogger` (a Nest `ConsoleLogger`) adds `trace_id` and `span_id` of the active span to text and JSON log lines, and `getTraceIds()` returns them for pino, winston and `nestjs-pino`. With `logs: { export: true }` and the optional packages `@opentelemetry/sdk-logs` and `@opentelemetry/exporter-logs-otlp-http` installed, every record is also sent over OTLP/HTTP to `/v1/logs`.
- d76bb8c: Method spans: no span for a non-entry method called outside a trace; `@Global()` root modules, several apps per process, and `*Service`/`*Repository` classes with enhancer-like method names are handled.
- 41b3510: Method spans (level 2). `NestFactory.create(AppModule, { instrument: NestrixInstrument })` traces the methods of the app's own controllers, services, repositories and BullMQ processors as `ClassName.method` spans nested under the request; `composeInstrument(NestrixInstrument, other)` combines it with another tool's `instrument`. "The app's own" classes are those the app's modules list statically, reached from the root module through static `imports`; providers registered by dynamic modules (`forRoot`, `register`, `forFeature`) and modules that define such factories are not traced unless named in `methods.include`. `methods.exclude` wins over everything, `methods.enhancers` opts in guard, pipe, interceptor and filter spans, and `methods.enabled: false` turns method spans off. `@Cron`, `@Interval` and `@Timeout` methods start a new trace per run, linked to the span active when they run; a processor's `process` is a child of BullMQ's consumer span when there is one. Methods are wrapped without `Proxy` and without touching prototypes, so method-level guards, `@HttpCode` and `Reflector` metadata keep applying. A method that returns a native promise returns a new promise that settles the same way, so the promise a traced method returns must be handled by its caller. Not applied under `@nestjs/testing`.
- d76bb8c: Metrics: `metrics.export` option; the owned meter provider starts at bootstrap so a host provider registered in `onModuleInit` wins; `url.scheme` on the request histogram.
- d16709a: Microservice tracing: SERVER spans for `@MessagePattern` and CONSUMER spans for `@EventPattern` handlers, parented on the trace context carried in the packet metadata (TCP, Redis, NATS, RabbitMQ, Kafka, MQTT 5); CLIENT spans for `send` and PRODUCER spans for `emit` on `ClientsModule` clients, with the trace context injected through the client's dispatch hook. `instrumentClient(client)` instruments a client created outside dependency injection, and `nestrixPreRequestHook` gives handler spans in a hybrid app (`connectMicroservice(options, { deferInitialization: true }).registerPreRequestHook(nestrixPreRequestHook)`).
- 42919f2: Node.js 26.13 or later is now required (`engines: >=26.13.0`). Node 22 and 24 are no longer supported.
- d99bd96: Outbound HTTP client spans for `node:http`/`node:https` and for `fetch`/undici (the copy bundled in Node and the `undici` package), from diagnostics channels: a child span of the active span, `traceparent` sent unless the caller set one, Nestrix's own export requests and suppressed contexts not traced, `ignore.outgoing` honoured, and query values and headers recorded under the privacy defaults.
- b92d662: Releases and users. `service.version` is now set on the Nestrix-owned resource from the new `serviceVersion` option, falling back to `resourceAttributes`, `OTEL_RESOURCE_ATTRIBUTES`, `GIT_SHA` and `npm_package_version`, and the dashboard's `meta` reports it. The opt-in `user` option reads the user behind a request (for example `(req) => req.user?.id`) and records it as `user.id` on the server span; it gets the same request object your guards see on Express, Fastify and platform-node. The query API's trace list gains `type` (`http`, `job`, `scheduled`, `other`), `release` and `user` on each item, and filters by all three.
- 6e6372c: Metrics: `http.server.request.duration` for every request (sampled or not) and runtime metrics (event-loop delay, V8 heap, RSS, CPU time), recorded through `@opentelemetry/api` so a host `MeterProvider` receives them. When Nestrix owns the tracer provider and exports traces, it also exports metrics over OTLP/HTTP to `/v1/metrics`, given the optional peers `@opentelemetry/sdk-metrics` and `@opentelemetry/exporter-metrics-otlp-http`. New option `metrics?: false | { runtime?: boolean }`.
- 7b06cb6: Query API: the lists and statistics accept an optional `service` parameter (traces, errors, routes, classes, map), and `meta` reports `mode` (`embedded` here) for the standalone server's multi-service API. The embedded dashboard serves one application, so a `service` other than its own name answers empty results.
- fdc3896: Dashboard: an SLOs page for the standalone server (objective, attainment, error-budget bar, 1 h and 6 h burn rates, create, edit and delete). It is hidden in an embedded dashboard.
- 8b3bc8c: Dashboard: slow (over 100 ms) database spans are highlighted in the trace waterfall, a Queries panel lists statements repeated three or more times with count and total time (picking one highlights its spans), a span's links open the linked trace when it is still in the store, and the request list gains a type filter (All, HTTP, Jobs, Scheduled), release and user filters, and release and user columns that show when a listed trace has them.
- a7fbe49: Dashboard for the standalone server: a service selector (shown when more than one service has data; the choice is in the URL and sent as `service` to the request, error, route, class and map queries), a map that lays several services out with their calls to each other drawn apart from their calls to external targets, a "standalone server" badge with a note that statistics come from stored spans, a sign-out button, and a redirect to the login page on a 401.
