## P15-01 as built

Protocol (all optional, additive; `packages/protocol/src/types.ts` and `dependencies.ts`, mirrored in `packages/nestjs/src/store/protocol-types.ts` and checked by `store-protocol.test.ts`):

- `DependenciesResponse`, `ClassStatsResponse`, `AppMapResponse` gain `previousCovered?: boolean`, `note?: string | null` (as `routes/compare`) and `previousTotals?` (present only when covered): `DependencyPreviousTotals { dependencies, calls, errors, slowestP95Ms }`, `ClassStatsPreviousTotals { classes, calls, errors, totalMs, ownMs | null }`, `AppMapPreviousTotals { targets, calls, errors, slowestP95Ms }`. The totals cover every target, class or edge of the previous window, including ones with no calls now.
- `DependencyStats.previous?`, `ClassStats.previous?`, `MapEdge.previous?`: that row's numbers in the previous window, counted the same way. Absent when not covered, or when the row had no calls then ("new").
- An older server sends none of these; the UI shows "—" with "This server does not send a previous window".

Backends: the previous window is the same query for the window just before (`now` moved to the last millisecond before the current window's first bucket or minute), merged by key (dependency id, class name, `from>to` edge). Coverage: embedded, the process's statistics start (`RouteStatistics.sinceUnixMs`, `ClassStatistics.sinceUnixMs`) must be at or before the previous window's start, and `classes` additionally needs the previous window inside the 60-minute ring, so a 60-minute `classes` is never covered; standalone, `min(route_minutes.minute)` of the service must reach the previous window's start (the Overview's rule). Not covered: `previousCovered: false`, a `note`, nothing else. The embedded dependencies and map read the trace store, which is capacity-bound, so an evicted previous window reads as fewer calls (the same bias as the current window). Standalone `classes` own time for the previous window is bounded above by the window's end (`ownUntilMs`) so it does not average in current spans; the SQL is the existing one-pass own-time query run twice. The service filter for another service answers empty with no totals.

UI: tiles take their change from the totals (`dependency-changes.ts`, `class-changes.ts`, `map-changes.ts`, helpers in `views/previous-window.ts`): counts as a neutral percentage, error rate in points and durations (slowest p95, own time) in ms, both worse when they rise. With a name filter on Dependencies the tiles sum the rows' own `previous` instead of the answer's totals. Rows: a "p95 change" column on the Dependencies table and the Map's edge table, an "Avg change" column on the Classes table (method rows leave it empty); "new" when a row has no previous; "—" with the note as tooltip when not covered. On the Map the first tile shows a change only when the app calls targets (one service); with several services it has none.

Tests: embedded `store-dependencies`, `store-app-map`, `class-stats-unit`, `dashboard-previous-window` (handlers with a fixed clock: covered, 60-minute ring, young statistics, other service) and HTTP assertions in the existing dashboard tests; standalone `test/query/previous-window.test.ts` against Docker Postgres; UI `views/previous-window.test.ts`; Playwright `e2e/p15-previous-window.pw.ts` (screenshots `p15-*`). Not benchmarked: the standalone endpoints now run their query twice plus one `min(minute)` lookup.

## P15-03 as built

- **Protocol** (`packages/protocol/src/remote-profiles.ts`): `InstanceRuntimeSample` { `cpuPercent?`, `eventLoopP99Ms?`, `heapUsedBytes?`, `rssBytes?`, `sampledAtUnixMs` }, optional as `CheckInRequest.runtimeSample` and `InstanceSummary.runtimeSample` (`null` when the latest check-in had none). The brief's name `runtime` was taken: both types already use `runtime` for `process.version`, so reusing it would have broken old servers and clients.
- **SDK** (`packages/nestjs/src/profiler/check-in-runtime.ts`, used by `remote.ts`): CPU over the interval since the previous check-in, heap and RSS read at check-in time (about 2 µs per check-in, no timer). Event-loop p99 comes only from the embedded dashboard's `RuntimeSampler.latest()`, when that runs and its sample is at most 30 s old. An own histogram was measured and not added: `monitorEventLoopDelay({ resolution: 20 })` on an idle Node 26.13 process cost 13.7 to 14.8 ms of CPU per 10 s, against 2.4 to 2.7 ms without it, plus about 47 wake-ups per second. So instances without the dashboard send no loop figure. Every source is guarded (`profiler.remote.runtime` in diagnostics); a failure leaves the figure or the field out and the check-in goes ahead.
- **Server**: `parseRuntimeSample` (`apps/server/src/profiler/parse.ts`, `RUNTIME_BOUNDS`): per-figure drop, never a `400`. Migration `0011_instance_runtime.sql` adds five nullable columns to `instances`, written by the check-in's existing upsert (NULL when absent, so an older SDK clears them). `GET instances` returns them with the server's time of that check-in as `sampledAtUnixMs`; the instance's clock is not used.
- **UI**: the standalone Profiler page has CPU and Loop p99 columns (kit `BarCell`; CPU against one core, or the largest when above), a stacked Heap / RSS column, "—" for a missing figure, and a "Suggested" chip per service (`packages/ui/app/views/profiler/instance-runtime.ts`). The chip needs at least two instances of the service reporting the figure, and the top one at least 1.5 times the next and at least 10 CPU points (else loop p99: 20 ms) above it. CPU goes first. To fit at 1280 px without pushing the Capture button out, the chip sits under the instance id and the PID under the host ("Host / PID"); a Playwright check measures that the table does not scroll at 1280 px.
- **Tests**: `packages/nestjs/test/profiler-check-in-runtime-unit.test.ts` (arithmetic, freshness, fault injection), `profiler-remote.test.ts` (body carries the sample, absent cleanly, throwing reader and dashboard source), `profiler-remote-nest.test.ts` (the dashboard's p99 reaches the check-in on Express, Fastify and platform-node). Server: `apps/server/test/profiler/unit.test.ts` (validation, old clients) and `remote-profiles.test.ts` (storage, clearing, another key cannot overwrite). UI: `instance-runtime.test.ts`, `e2e/profiler-remote.pw.ts` (columns, "—", chip, older server, phone width) and the P14 standalone screenshot fixture.
- **Deferred:** the loop figure for instances without the embedded dashboard (needs the owner or lead to accept the histogram's cost, or a cheaper source); an OTLP metrics receiver (D-80).

## P15-02 as built (Errors data)

Protocol (all optional; `packages/protocol/src/error-groups.ts`, mirrored in `packages/nestjs/src/store/protocol-types.ts` with a drift check in `test/store-protocol.test.ts`): `ErrorGroup` gains `state` (`ErrorGroupState`: `new` | `regressed` | `ongoing` | `quiet`), `firstEverUnixMs`, `lastEverUnixMs`, `firstSeenRelease`, `lastSeenRelease` and `releases` (`{ release, count }[]` in the window, at most 5); `ErrorGroupsResponse` gains `history` (`{ fromUnixMs, toUnixMs }`, the stored history the state and first-seen were computed over). `firstSeenUnixMs`/`lastSeenUnixMs` stay window-scoped (the existing columns use them); the whole-store times are the new `*EverUnixMs` fields. New `GET <path>/api/v1/errors/insights?route=&service=` answers `ErrorInsightsResponse`: `heatmap` (7 rows Monday to Sunday of 24 hourly counts, UTC), `total`, `releases` (`ErrorReleaseStat`: `events`, `requests`, `per1000Requests`, `firstSeenUnixMs`; the newest 8 releases, oldest first; releases with neither events nor requests are left out), `fromUnixMs`/`toUnixMs` (7 days) and `coveredFromUnixMs` (where stored data starts inside that range; the embedded store keeps hours, so the card says "last N hours"). Only `service` and `route` filter it (the exception type is in the events JSON on the server, not cheap).

State rules (`stateOf` in `error-groups.ts`, first match wins): **quiet** = no occurrence in the last two buckets of the window (checked first, as the old UI did); **new** = no stored occurrence before the window; **regressed** = seen before the window and either at least 24 hours (`REGRESSION_GAP_MS`) passed between its last pre-window occurrence and its first one in the window, or a release was first seen in between that the group's first in-window occurrence is not in (it skipped a whole release; releases are known only from stored error occurrences, so a release with no error never counts); **ongoing** = the rest. Occurrences before the window never create groups, they only give the groups of the window their history. A group seen only in a quiet gap shows Quiet even when it is a regression.

Backends: embedded (`TraceStore.groupErrors` already read every stored error, so the history is whatever the ring holds; `TraceStore.errorInsights` walks the listed traces for requests per release and the error list for events, both bounded by the store's own limits). Standalone (`QueryService.errorGroups` runs two queries, the window as before (newest 5,000) and the 7 days before it (newest 20,000, `WINDOW_ROW_CAP`/`HISTORY_ROW_CAP`); `history.fromUnixMs` is the oldest row read when the cap was hit, else 7 days ago. `errorInsights` is three aggregates (`GROUP BY` weekday/hour from `spans`; events per `traces.release`; requests (`trace_type = 'http'`) and first seen per release from `traces`), no row reads). `apps/server/src/query/error-groups.ts` and `error-insights.ts` are copies of the embedded modules (only the import line and the header differ), each with the same unit tests in both packages. A release is the trace's `service.version` (`traces.release` on the server); errors per 1,000 requests count requests as traces with an HTTP root, so a service with no HTTP traffic shows events only (the card says so).

UI (`views/errors/`): the state comes from the server (`groupState` falls back to the series for an older backend, never "Regressed"); chips are New (worse), Regressed (warn), Ongoing (info), Quiet (neutral); a fifth tile "Regressed"; a Release column last in the groups table ("1.0.0 → 1.2.0" when the first release differs, tooltip with the window's per-release counts); the "When errors happen" heatmap card (kit `Heatmap`, UTC, busiest cell in the label and the note) and the "Errors per release" bar chart (per 1,000 requests when every release has requests, otherwise events, labelled), both below the existing charts and only shown when the page has groups; a backend without the endpoint just has no extra cards. Tests: `error-groups-state-unit.test.ts` and `error-insights-unit.test.ts` (nestjs and server), `dashboard-error-insights.test.ts` (embedded routes), `apps/server/test/query/error-insights.test.ts` (against Postgres), `store-protocol.test.ts`, `errors-stats.test.ts`, `e2e/p15-errors-data.pw.ts` (screenshots `p15-errors-dark.png` / `-light.png`). `e2e/p14-errors-queries.pw.ts` now expects 5 tiles.
