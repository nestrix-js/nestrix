## Settled design (refined by the spike, P7-S1)

- **Profiler: on demand only, never continuous** (D-56). A capture runs for a bounded time (default 30 s, at most 120 s), one at a time per process. Profiles are kept in memory (the last three) and downloadable as `.cpuprofile` (Chrome DevTools format), with a top-functions table and a flame graph in the dashboard. Nothing runs when not capturing. Details from [P7-S1](../spikes/P7-S1.md), "Chosen approach":
  - *API.* `process.getBuiltinModule("node:v8").startCpuProfile({ sampleInterval: 1, maxBufferSize })`, called only when a capture starts; `handle.stop()` returns the profile as a JSON string, and `handle[Symbol.dispose]()` discards it. No `inspector.Session` and no `Debugger` domain. `maxBufferSize` is set from the duration (`ceil(durationMs / 1) + 1000`) to cap the samples kept.
  - *One at a time.* The API does not refuse a second concurrent capture, so Nestrix keeps a process-wide slot (`globalThis[Symbol.for("nestrix.profiler")]`, shared by package copies and apps in one process). A second request gets `409`. There is no refusal on an open debugger port (`inspector.url()`) or on other profilers: the spike found an attached debugger, an APM-style `Session` and `node --cpu-prof` undisturbed, and refusing would disable the feature under `--inspect`.
  - *Lifetime.* The end timer is `unref()`'ed. `onApplicationShutdown` discards a running capture. Every call is guarded: `startCpuProfile` can throw, and `stop()` can return `undefined`. A failure frees the slot, is logged once, and is shown in the dashboard.
  - *Output.* After stop, off the request path, the profile is normalised to `node --cpu-prof`'s form: numeric `scriptId` to string, absolute-path `url` (CommonJS) to a `file://` URL. The result is kept as a string with its metadata: start, duration, `startMs`, samples, bytes. In the spike's app, a 30 s capture was 0.3 MB of JSON and 120 s was 0.9 MB.
  - *Overhead (measured).* Throughput and p99 during a capture at 1 ms or 10 ms: no difference this benchmark resolves (under about 5% on a trivial route; `/cpu` −1.6% to −4%, inside run-to-run noise). **Starting a capture blocks the main thread** while V8 logs existing code, on every capture and with any API: about 10 ms per MB of compiled code plus bytecode, so 36 to 47 ms in a minimal Nest app and 230 ms with 22 MB of code. The endpoint returns the measured `startMs`. The UI warns before starting and may estimate the pause from `v8.getHeapCodeStatistics()`. The docs state these numbers. Stop takes 2 to 5 ms.
  - *Stated limits (docs and UI).* Main-thread JavaScript only (no worker threads); lines of the running JavaScript (no source maps); inlined functions can appear under their caller, more often after the first capture in a process (a V8 profiler behaviour).
- **Starting a capture is the dashboard's first state-changing action**, so it gets protection beyond the read-only rules of architecture §4.7: `POST` only; `Sec-Fetch-Site` must be `same-origin`; `Origin` must equal the request's host; available only when the dashboard is on and authenticated (`ui.enabled: true` with `auth`, or `'auto'` with the startup token). `ui.profiler: false` disables it.
- **Alerting (standalone server):** rules on route and class statistics from the rollup tables, `error_rate > x` or `p95_ms > y` over a window (5 to 60 minutes), per service and optionally per route; evaluated every minute; states `ok`, `firing`, `resolved`, with a minimum duration against flapping; notifications by webhook (JSON `POST`, body signed with HMAC-SHA256 using a per-rule secret, 5 s timeout, retries with backoff, one in flight per rule). Rules are managed through the admin-protected API (`/api/v1/alerts`) and stored in Postgres. Outbound requests: `http`/`https` only, redirects not followed, private, link-local and loopback addresses refused unless listed in `NESTRIX_WEBHOOK_ALLOWED_HOSTS` (SSRF).
- **SLOs (standalone server):** an objective per service or route, availability (share of non-5xx) or latency (share under a threshold), over a rolling 7 or 30 days, computed from the rollups; the API reports attainment, remaining error budget and burn rate over 1 h and 6 h; burn-rate alerts reuse the alerting engine. A UI page lists SLOs with budget bars.

## Acceptance (delivery mode: functional checks, local)

- A capture started from the dashboard on all three adapters returns a valid `.cpuprofile` (JSON with `nodes`, `samples`, `timeDeltas`), shows the hot function of a CPU-bound test route at the top, and leaves request results unchanged; a cross-site, wrong-origin or unauthenticated request cannot start one; a second start while one runs is refused. For a stable "hot function at the top", run the app in a fresh child process, warm the route before the first capture, and find the function by name, as `spikes/p7-s1/probes/nest-capture.mjs` does. In a test process that has already captured, the function's samples can land on its inlining caller.
- An alert rule on a service whose error rate rises above the threshold fires once, sends one signed webhook to a local receiver, and resolves when the rate drops; a webhook to a loopback URL is refused unless allowed.
- An SLO over seeded rollups reports the expected attainment and budget.
