## Settled design (before the spike)

- **Profiler: on demand only, never continuous** (D-56). A capture runs for a bounded time (default 30 s, at most 120 s), one at a time per process, through a public Node API (the spike chooses between `node:inspector` `Profiler.start/stop` in the same thread and any newer V8 profiling API Node 26 offers). Profiles are kept in memory (the last three) and downloadable as `.cpuprofile` (Chrome DevTools format), with a top-functions table and a flame graph in the dashboard. Overhead during a capture is measured in the spike (a short benchmark) and stated in the docs; nothing runs when not capturing.
- **Starting a capture is the dashboard's first state-changing action**, so it gets protection beyond the read-only rules of architecture §4.7: `POST` only; `Sec-Fetch-Site` must be `same-origin`; `Origin` must equal the request's host; available only when the dashboard is on and authenticated (`ui.enabled: true` with `auth`, or `'auto'` with the startup token). `ui.profiler: false` disables it.
- **Alerting (standalone server):** rules on route and class statistics from the rollup tables, `error_rate > x` or `p95_ms > y` over a window (5 to 60 minutes), per service and optionally per route; evaluated every minute; states `ok`, `firing`, `resolved`, with a minimum duration against flapping; notifications by webhook (JSON `POST`, body signed with HMAC-SHA256 using a per-rule secret, 5 s timeout, retries with backoff, one in flight per rule). Rules are managed through the admin-protected API (`/api/v1/alerts`) and stored in Postgres. Outbound requests: `http`/`https` only, redirects not followed, private, link-local and loopback addresses refused unless listed in `NESTRIX_WEBHOOK_ALLOWED_HOSTS` (SSRF).
- **SLOs (standalone server):** an objective per service or route, availability (share of non-5xx) or latency (share under a threshold), over a rolling 7 or 30 days, computed from the rollups; the API reports attainment, remaining error budget and burn rate over 1 h and 6 h; burn-rate alerts reuse the alerting engine. A UI page lists SLOs with budget bars.

## P7-03 as built

- **Tables** (`migrations/0002_alerts.sql`, Drizzle in `src/storage/schema.ts`): `alert_rules` (`metric` `error_rate` | `p95_ms`, `comparator` `>` only, `threshold` (error rate as a fraction, p95 in ms), `window_minutes` 5–60, `for_minutes` 0–60 default 2, `min_requests` 1–1 000 000 default 10, `webhook_url`, `secret`, `enabled`), `alert_state` (one row per evaluated rule: `ok` | `pending` | `firing`, `since`, `last_value`, `last_notified_at`; "resolved" is the firing → ok transition), `alert_events` (`firing` | `resolved` | `test`, delivery `pending` | `sent` | `failed` | `refused`, attempts, status, a short error category; deleted after `NESTRIX_RETENTION_DAYS`). Deleting a rule deletes its state and history.
- **Metrics** (`src/alerts/metrics.ts`): from `route_minutes` over the last `window_minutes` minute buckets, current minute included (`minute > now - window`, `minute <= now`); with `route`, that route under every method. Errors are the rollup's (status error or 5xx). p95 from the summed histograms (`estimateQuantile`). Fewer requests than `min_requests` is **no data**, which changes no state: a firing alert is not resolved by silence (a dead service sends nothing), a pending one does not fire. `class_minutes` is not used yet.
- **State machine** (`src/alerts/state.ts`, pure): ok + breach → pending (or firing at once when `for_minutes` is 0); pending held for `for_minutes` (5 s tolerance for timer drift) → firing, notify; pending without breach → ok, silent; firing without breach → ok, notify resolved. Disabling a rule or changing its service, route or metric resets the state silently.
- **Evaluator** (`src/alerts/evaluator.ts`): every 60 s after a 10 s delay (unref'd timer; a tick during a run is skipped). A run takes `pg_try_advisory_lock(ADVISORY_CLASS, ALERTS_LOCK = 4)` on one connection and skips when another instance holds it; each rule is evaluated in its own transaction (`FOR SHARE` on the rule, `FOR UPDATE` on its state), and the event row is written with the state change. Webhooks go out after the commit; the event row is then updated. A crash in between leaves the event `pending` and unsent (at most once).
- **Webhook** (`src/alerts/webhook.ts`): `POST` JSON (`AlertWebhookPayload` in `@nestrix/protocol`), `x-nestrix-timestamp` (Unix seconds) and `x-nestrix-signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<body>">` with the rule's secret (`whsec_` + 32 random bytes base64url, returned only by create, stored in clear because the server signs with it). 5 s per attempt, 3 attempts, backoff 1 s then 2 s, retried on network errors, timeouts, 408, 429 and 5xx; a 3xx is a failure, never followed or retried; the response body is never read. One delivery in flight per rule, at most 16 queued behind it. SSRF: `http`/`https` only, no credentials in the URL; the host is resolved once per attempt and refused if **any** address is not public unicast (`src/alerts/address.ts`: private, CGNAT, loopback, link-local, unique-local, site-local, multicast, unspecified, documentation, benchmarking, reserved, Teredo, IPv4-compatible, and the IPv4 inside IPv4-mapped, NAT64 and 6to4 addresses), unless the URL's host is in `NESTRIX_WEBHOOK_ALLOWED_HOSTS` (comma-separated host names or IPs, no ports); the socket connects to the checked address (`Host` and TLS SNI/verification use the name). Literal private addresses are also refused by the API on create and update.
- **API** (`src/alerts/alerts.controller.ts`, types in `packages/protocol/src/alerts.ts`, types only): `GET /api/v1/alerts`, `POST` (201 `{ rule, secret }`), `GET|PATCH|DELETE /api/v1/alerts/:id`, `POST /api/v1/alerts/:id/test` (one attempt, recorded as a `test` event), `GET /api/v1/alerts/events?rule=&limit=` (newest first, 1–200, default 50). Unknown fields and parameters are 400. Covered by the admin middleware and global guard (401 signed out; state-changing methods need a same-origin `Origin`), plus `SessionQueryGuard` on the controller.
- **Configuration:** `NESTRIX_WEBHOOK_ALLOWED_HOSTS`, and `NESTRIX_PUBLIC_URL` (optional; the dashboard link in payloads, `null` without it).
- **For P7-04 (burn-rate alerts):** add a metric function to `METRICS` in `metrics.ts` (signature `(db, rule, nowMs) => Promise<number | null>`, `null` for no data), a new `metric` value in a migration's `CHECK` (and a column such as `slo_id` if the rule needs one), and reuse `transition()` and the evaluator unchanged; the threshold is then a burn-rate multiple.

## P7-04 as built
- **Storage:** `migrations/0003_slos.sql`: table `slos` (service, optional route, kind `availability` | `latency`, `latency_threshold_ms` for latency only, `objective` strictly between 0 and 1, `window_days` 7 or 30), `alert_rules.slo_id` (cascade delete) and the `slo_burn_rate` value in the metric check (a rule has an `slo_id` exactly when its metric is `slo_burn_rate`).
- **Formulas** (`src/slos/compute.ts`, sums of `route_minutes` with `now - period < minute <= now`, any method; a route SLO reads that route, otherwise every route of the service). Availability: bad = `errors`, the rollup's definition (span status error or HTTP 5xx; a thrown 4xx is not an error). Latency: good = requests faster than the threshold, estimated from the histogram (buckets whose upper bound is at or below the threshold in full, the bucket holding the threshold in proportion, linear inside the bucket; so the result is as exact as the histogram, about 48% bucket width); bad = count - good. attainment = good / count; budget = (1 - objective) * count; remaining = budget - bad (negative when overspent; fraction = remaining / budget); burn rate over a period = (bad / count) / (1 - objective), over the last 1 h and 6 h; `null` without requests. `breached` is attainment below the objective.
- **API** (`src/slos/`, types in `packages/protocol/src/slos.ts`): `GET|POST /api/v1/slos`, `GET|PATCH|DELETE /api/v1/slos/:id`; the status is computed on every read. Access as alerts (session, same-origin `Origin` on writes, no CORS).
- **Burn-rate alerts:** `POST /api/v1/alerts` with `metric: "slo_burn_rate"`, `sloId`, `threshold` (a multiple, above 0 up to 1000, e.g. 14.4) and `windowMinutes` (5 to 60, the burn-rate window, e.g. 60). `service` and `route` are not given: they are copied from the SLO at create or when `sloId` changes. The metric reads the SLO at each evaluation (so editing the SLO applies at once). `min_requests` applies to the window. The webhook payload is unchanged (`metric: "slo_burn_rate"`, `value` is the burn rate).
- **UI:** an "SLOs" tab shown only when `meta.mode` is `standalone` (the `#/slos` route in an embedded dashboard says SLOs need the standalone server): objective, attainment, budget bar, 1 h and 6 h burn rates, create/edit form (fetch, not a form post), delete with a confirmation. The page does not manage burn-rate alert rules; they are created through the API.

## Acceptance (delivery mode: functional checks, local)

- A capture started from the dashboard on all three adapters returns a valid `.cpuprofile` (JSON with `nodes`, `samples`, `timeDeltas`), shows the hot function of a CPU-bound test route at the top, and leaves request results unchanged; a cross-site, wrong-origin or unauthenticated request cannot start one.
- An alert rule on a service whose error rate rises above the threshold fires once, sends one signed webhook to a local receiver, and resolves when the rate drops; a webhook to a loopback URL is refused unless allowed.
- An SLO over seeded rollups reports the expected attainment and budget.
