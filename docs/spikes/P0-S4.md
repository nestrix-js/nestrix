The Jest failure text, identical on all three Nodes with the default config:

```
Must use import to load ES Module: .../packages/nestjs/dist/index.js

The file contains ESM syntax (import/export) that could not be executed as CommonJS. Either:
  - Configure a transform (e.g. babel-jest) that compiles this file to CommonJS ...
  - If the file is in "node_modules", allow it to be transformed by adjusting "transformIgnorePatterns" ...
  - Use Node v24.9+ where Jest supports require(esm) natively ...
  at createRequireEsmError (jest-runtime/build/index.js:452:17)
```

Cause (verified): Jest's native `require(esm)` path is gated at `jest-runtime@30.5.2/build/index.js:4442-4444` on `typeof vm.SourceTextModule?.prototype.hasAsyncGraph === 'function'`. `vm.SourceTextModule` exists only under `--experimental-vm-modules` (`typeof require("vm").SourceTextModule` is `undefined` without it on all three Nodes). With the flag, `hasAsyncGraph` is `undefined` on 22.15.0 and a `function` on 24.22.2 and 26.13.0, which is exactly the pass/fail split in the table. The error text ("Use Node v24.9+ where Jest supports require(esm) natively") therefore omits the flag: 24.22.2 and 26.13.0 fail without it. The `@nestjs/schematics` 12.0.13 CommonJS starter already runs `node --experimental-vm-modules ./node_modules/jest/bin/jest.js` (`application/files/ts/package.json.template`, lines 17-21, per the review), so this is how Nest's own CJS projects work; research.md §1 is incomplete rather than wrong. The error before Node 24.9 is `Must use import to load ES Module`, not `ERR_REQUIRE_ASYNC_MODULE`.

The transform route works on all three Nodes, including a module using `import.meta.url` (swc rewrites it). What it did not cover: a Nest app with decorators defined in the Jest test files themselves (our tests only load precompiled code). Decorators written inside Vitest test files were not tested here either (P0-05 covers that for Vitest in its own package).

## The check (`scripts/check-no-tla.mjs`)

Location and reason: `scripts/` at the repo root, not under the spike, because it checks the *published* packages (workspace-wide), not the spike; spikes are throwaway and the check must outlive this one. Needs `pnpm build` first. No dependencies beyond Node.

Every check is "`require()` it in a fresh child process, from the package directory", so Node's own parser, resolver and conditions decide. For each workspace package under `packages/` and `apps/` without `private: true`:

1. Every JavaScript entry in its `exports` map (wildcard patterns and `./package.json` skipped): `require("<name>[/subpath]")` by self-reference. The whole static graph, dependencies included, is evaluated. Any error fails. On `ERR_REQUIRE_ASYNC_MODULE` it re-runs with `--experimental-print-required-tla` to print where the `await` is.
2. Every built `.js`/`.mjs` file under `dist/`, not only the entries: `require("<absolute path>")`. This finds a TLA in a file reached only through `import()`. Here `ERR_REQUIRE_ASYNC_MODULE` and `SyntaxError` fail; any other load error (a file that needs a global or peer at load time) is printed as a `note`.

Both also fail on an `ExperimentalWarning` on stderr (loading must not need flags or print experimental warnings); this is stated in the script's header comment. Not covered: a TLA in a dependency's file reached only through `import()` (it cannot break `require()` of our entry). The result depends on the Node running it, so run it on every Node in the CI matrix; I ran it on 22.15.0, 24.22.2 and 26.13.0.

History: my first version replaced step 2 with a syntactic scan (TypeScript AST). The review showed it skipped function and class nodes wholesale and so missed `class D extends (await p) {}`, `class C { [await p]() {} }`, `{ [await p]() {} }` and `await using`. Asking Node is simpler and has no such blind spots.

Demonstrations. Entry-file TLA (first version of the check, `export const lateValue = await Promise.resolve(1);` appended to `packages/nestjs/src/index.ts`): `FAIL require("@nestrix/nestjs")` with `index.js:3`, the source line and `ERR_REQUIRE_ASYNC_MODULE`, exit 1. A TLA in a temporary `node_modules/tla-dep` imported by the entry: `FAIL require("@nestrix/nestjs")` pointing at `node_modules/tla-dep/index.js:1`, exit 1.

For the final version, four hand-written files were placed in `packages/nestjs/dist/` (not imported by the entry, i.e. "lazy"; hand-written because TypeScript would not emit some of the forms for this target), then removed:

| File content | Result on 22.15.0 / 24.22.2 / 26.13.0 |
|---|---|
| `const p = Promise.resolve(class {}); export class D extends (await p) {}` | `FAIL ... ERR_REQUIRE_ASYNC_MODULE`, exit 1, on all three |
| `export class C { [await p]() {} }` | same |
| `export const o = { [await p]() {} };` | same |
| `await using r = { async [Symbol.asyncDispose]() {} };` | 24.22.2 and 26.13.0: `ERR_REQUIRE_ASYNC_MODULE`, with the location printed (`await using r = ...` with a caret); 22.15.0: `SyntaxError: Unexpected identifier 'r'` (not a valid module there at all). Both fail the check. |

With the four files present the run ended `check-no-tla: 4 problem(s)`, exit 1; `require("@nestrix/nestjs")` itself stayed `ok`, so the per-file pass is what caught them. After removal, `git status` shows `packages/` unchanged and `pnpm check:tla` passes.

Two operational notes. `tsc -b` does not delete outputs of removed sources, so a stale file in `dist/` is still checked; locally `rm -rf packages/*/dist` before trusting a result (CI starts clean). And `pnpm test` now runs the spike's Vitest project, which loads `dist-esm/` from `pnpm build`, so `pnpm test` alone on a fresh checkout fails until a build has run (`verify` builds first).

**CI wiring.** Main's `verify` matrix already runs `pnpm verify` on every Node, and `check:tla` is inside `verify`, so no workflow change is needed.

## Extra findings

- **Dual `@opentelemetry/api` and SDK instances in a CommonJS host.** The OTel packages are dual-built, so a CJS host that `require()`s them gets the `.cjs` copies while `@nestrix/nestjs` (ESM) gets the `.mjs` copies. `scripts/q3c-dual-api.cjs` is a real CJS host (provider and `InMemorySpanExporter` from the `.cjs` `@opentelemetry/sdk-trace`) with Nestrix using only the ESM `@opentelemetry/api`, and asserts on all three Nodes: the two api objects differ; host `setGlobalTracerProvider` returns `true` and Nestrix's call through the ESM copy returns `false`; a span started with the ESM tracer reaches the host's exporter; a span set into a context with the CJS copy is read back with the ESM copy's `trace.getSpan` (context keys are `Symbol.for`); a child started by the ESM tracer in that context has the host span as parent and the same trace id; and `esmExporter instanceof hostSdk.InMemorySpanExporter` is `false`. So the "returns false means a provider exists" design in architecture.md 4.5 holds across module formats, but `instanceof` does not. Context propagation with a real context manager (async context across the two copies) was not tested: that is left to P0-S3.
- **pnpm 12 fails `pnpm install` on unreviewed build scripts** (`ERR_PNPM_IGNORED_BUILDS`). Jest brings `@parcel/watcher` and `@swc/core` brings its own. I added `allowBuilds: { "@parcel/watcher": false, "@swc/core": false }` to the root `pnpm-workspace.yaml` (written by `pnpm approve-builds`); neither is needed here (SWC loads its prebuilt binary from an optional dependency). It will recur for any future dependency with a build script.
- **The spike adds Jest and SWC** (`jest`, `@swc/jest`, `@swc/core`), about 3.7k lines of `pnpm-lock.yaml` and the two `allowBuilds` entries. Remove all of it when the spike is retired.
- **attw's `esm-only` profile, which `check:packages` uses, ignores the CJS-consumer rows** ("A require call resolved to an ESM JavaScript file", `node16 (from CJS)` is `(ignored) ESM (dynamic import only)`). It reports ESM-only as acceptable but does not verify that `require()` works. `check:tla` does.

## Chosen approach

The design in architecture.md stands: ship ESM-only, keep the entry graph free of top-level `await`, and let CommonJS Nest 12 apps `require()` it. Nothing needed flags on Node 22.15, 24 or 26, and decorators and `reflect-metadata` behave. Enforce the no-TLA rule with `pnpm check:tla` (require every published entry and every built file in a child process), in `verify` and on each CI Node. Document Jest in CommonJS projects as Nest's own requirement (`--experimental-vm-modules` on Node 24.9+, a transform on 22.x).
