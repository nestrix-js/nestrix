# P0-S2 Library spans without a preload

2026-11-11. Node 22.15.0, 24.22.2 and 26.13.0 (darwin-arm64; 22 and 24 from nodejs.org tarballs). NestJS 12.4.2 with `@nestjs/platform-express`, `-fastify` and `-node` 12.4.2. `@opentelemetry/api` 1.10.0, `@opentelemetry/sdk-trace` 3.1.1, `@opentelemetry/context-async-hooks` 3.1.1, `@opentelemetry/core` 3.1.1, `@opentelemetry/instrumentation-undici` 0.35.0. `pg` 8.23.1 (and 8.20.0 for the nested case), `pg-cursor` 2.22.1, `pg-query-stream` 4.17.1, `mysql2` 3.24.6, `ioredis` 6.0.0 and 5.11.1, TypeORM 1.1.2, Drizzle ORM 0.45.4, MikroORM 7.2.8, Prisma 7.10.1 with `@prisma/adapter-pg` 7.10.1. pnpm 12.16.1. PostgreSQL 18.6, MySQL 8.4.13, Redis 8.10.3 in Docker 29.5.2. Every version came from `npm view` or the installed manifest.

Code: `spikes/p0-s2/`. The stand-in for `@nestrix/nestjs` is `src/nestrix/` (ESM). It is switched on by `SpikeNestrixModule.forRoot()` inside the app's `@Module` decorator, so it runs while the app's own module graph is evaluated. Two fixture apps load it: an ESM Nest app (`src/fixture/`) and a CommonJS Nest app (`cjs/src/main.ts`, which loads the ESM stand-in with `require(esm)`). Each is run as a child process with plain `node <file>`. Every result records `process.execArgv` (always `[]`) and `NODE_OPTIONS` (always empty), and the test runner removes `NODE_OPTIONS` and `NODE_PATH` before spawning. Instrumentation code imports `@opentelemetry/api` only. The SDK is touched in `src/nestrix/tracing.ts` alone, which registers `AsyncLocalStorageContextManager` from `@opentelemetry/context-async-hooks` 3.1.1 (peer `@opentelemetry/api >=1.0.0 <1.11.0`), because SDK 3 ships only `StackContextManager`.

An independent review accepted this result after fixes F1 to F8; this version includes them.

Rule 1, shown with tests (`rule1-and-dual-api.test.ts`):
- With a fault injected into every guarded body, every fixture route returns the same body as without (ids, ports and the Redis counter normalised). Failures are counted, and node:http sends no `traceparent`.
- **Labelled demonstration** (`scripts/unguarded-subscriber.mjs`). An unguarded subscriber that throws on `http.client.request.created` does not interrupt the request, which completes with 200, but Node re-throws the error as `uncaughtException`. With no handler, the process exits with code 1 and prints the subscriber's stack. An unguarded `ioredis:command` `start` subscriber behaves the same way: one `uncaughtException` per command.

A spike bug, found and fixed. The first `pg` client wrapper called the original from inside its guarded `try`, so a synchronous throw from pg itself (the null-query `TypeError`) was counted as a Nestrix failure and pg was called a second time. The rule for every wrapper is: decide inside the guard, call the original once, outside it. Test: "a synchronous throw from pg reaches the caller once, and pg is called once".

**Pool wait time.** The `pg` pool span starts at `pool.query()` and includes waiting for a connection. The mysql2 query span starts when the query is sent and excludes it. Proposed single rule: a database span covers only the query (as the mysql2 channel and pg's own Client spans already do), and pool wait, where it matters, is a separate measure (OpenTelemetry has a `db.client.connection.wait_time` metric). For `pg`, the pool wrapper would then record the caller's context with the token and let the client wrapper open the span with that parent when the inner query starts. Not implemented; it is a proposal.

Further findings, outside the seven questions but on their path:
- **`@opentelemetry/api` is a dual package** (`exports`: `require` → `dist/index.cjs`, `default` → `dist/index.mjs`). In a CommonJS app, user code gets the CJS build and the ESM-only Nestrix gets the ESM build. A tracer the app takes at module top level, before Nestrix registers the provider, **stays a no-op forever** (`scripts/dual-api.cjs`: `earlyRecording: false, earlySpanId: "0000000000000000"`; ESM control `scripts/dual-api.mjs`: recording). **Review F5 control** (`scripts/dual-control.cjs`, test "F5 control…"): the early CJS tracer delegates when the provider is registered through the same CJS instance (`earlyDelegates: true`), and never when it is registered through the ESM build (`false`); tracers taken after registration delegate in both cases. Cause: each API module instance keeps its own private `ProxyTracerProvider`, and only the registering instance's proxy gets the delegate. Candidate fix (untested in a Nestrix setup): in a CJS app, register through the CJS instance, reached from the ESM package with `createRequire`. That would only move the problem to tracers taken early from the ESM instance. P0-S3 reached the same practical rule: always call `getTracer()` at use time. The first CJS fixture run showed the hazard (every handler span a no-op, every library span a root); the fixture now takes its tracer per call. With that, async context does carry across the two API copies under a real ALS context manager (CJS handler span → ESM-instrumentation child spans, all three Node versions), which P0-S4 left open.
- pnpm's bin shims (`node_modules/.bin/*`) export `NODE_PATH` that includes `node_modules/.pnpm/node_modules`. An app launched through a shim (for example `nest start`) can therefore resolve any hoisted `pg` from anywhere (test "finding: NODE_PATH from a pnpm bin shim…").
- The registry's `latest` for `prisma` is `8.0.0-rc.33` (a release candidate), while `@prisma/client` and `@prisma/adapter-pg` `latest` are 7.10.1. `npm view prisma version` is not a safe way to pick "Prisma 7".
- The registry's `latest` for `ioredis` is 6.0.0. Its `ioredis:command` channel behaves like 5.11.1's (the sanitiser list differs slightly: 6.0 adds `GETSET`/`PSETEX` to the "first argument safe" group).

## What this changes

Proposals only. The spike did not edit these files.

**architecture.md**
- §4.2 Outbound HTTP, `node:http`: remove the **(spike)** marker and state the mechanism:
  - start the span in `http.client.request.created`, with the caller's active context;
  - inject `traceparent` only when the request has none, and tolerate a `setHeader` failure (array headers) silently;
  - end the span on the response's `close` (attached from `http.client.response.finish`; error if `!response.complete`) or on `http.client.request.error`;
  - if, on the `setImmediate` after `response.finish`, nothing is consuming the body, end at the response head and mark the span `body: not consumed` (otherwise the span never ends);
  - a caller that starts reading on a later tick gets a head-only span.
- §4.2 / §4.5 fetch: add that `@opentelemetry/instrumentation-undici` brings `@opentelemetry/instrumentation` with `require-in-the-middle` and `import-in-the-middle`, and that constructing it installs a process-wide `Module.prototype.require` hook. Either accept that and say so (startup and per-`require` cost to be measured in phase 1), or write a first-party `undici:request:*` subscriber like the `node:http` one. Owner and lead decide; this would revisit D-13.
- §4.4 table:

  - ioredis: add the known gaps (offline-queue commands become root spans; handshake commands are root spans) and a rule for root `redis` spans (drop them, or keep them only if the user opts in).
  - `pg`:
    - Replace "Works without a preload because…" with what was verified: the module object is shared for ESM `import` and CJS `require` alike.
    - Add the pool/client de-duplication requirement: a reference-counted mark per pool call (not a set). Note its residual ambiguity when the same config object is used directly on a client while a pool call with it is queued.

Candidate: also wrap every `pg/lib/index.js` already in `require.cache`. Verified in plain-node probes; scan timing in a Nest app (at enable, at `onApplicationBootstrap`) **unverified**; copies loaded later are missed.

**Decisions affected**
- **D-3** ("switch on when the library is present"), together with rule 1. Switching on mysql2 or ioredis changes host behaviour from *crash* to *silence* (Q7). No subscription style avoids it, because the trigger is the channel's combined `hasSubscribers`. **Owner decision needed.** The options, without a recommendation:
  - (a) default-on, and document both behaviour changes;
  - (b) opt-in per integration;
  - (c) prototype wrapping like `pg` instead of channels: avoids the change, but brings back the nested-copy and optional-peer resolution issues and patches library internals;
  - (d) subscribe only to channels whose subscription does not change behaviour, which means no query or command spans. For mysql2, a `mysql2:pool:connect`-only subscriber left all 48 observations unchanged (test "option (d): subscribing only to mysql2:pool:connect changes nothing", all three Node versions); `connect` channels were not checked.
- **D-13** (reuse upstream for undici): still workable, but it costs a global require hook and two loader libraries in the dependency budget (§4.5). Worth an explicit yes from the owner.
- No decision-log entry was reopened.

## Chosen approach

The architecture's mechanisms stand, with corrections:
- **undici:** the upstream instrumentation, enabled at module initialisation, works in ESM and CJS on all three Node versions.
- **`node:http`:** the first-party channel subscriber works, provided it ends on response `close`, falls back to the head when the body is not consumed, and does not override a caller's `traceparent`.
- **mysql2 and ioredis:** TracingChannel subscribers work for ordinary calls. mysql2 needs the `pool:connect` context fix; `bindStore` is the complete version once Nestrix owns its context manager. ioredis has two documented gaps (offline queue, handshake). Whether they are on by default is the D-3 question above.
- **`pg`:** `createRequire` plus prototype wrapping is sound under pnpm's strict layout, for ESM and CJS apps, raw `pg`, TypeORM, Drizzle and Prisma. It needs reference-counted pool/client de-duplication, and on its own it misses nested copies. I recommend adding the `require.cache` scan to the mechanism, with its timing verified in a Nest app first. That is an addition to the chosen mechanism, not a switch, and it is the lead's and owner's call.

## Left open

- **Cache-scan timing in a Nest app** (at enable, at `onApplicationBootstrap`) and a `pg` copy loaded after the last scan (an ORM imported lazily). Answering it needs a Nest fixture with MikroORM (eager and lazily imported) and the scan wired into the module lifecycle.
- **MikroORM in its default install** (app `pg` ≠ 8.23.1): only the forced override was tested. The exact-pin finding comes from the manifest and predicts the same result, but that is inferred, not run.
- **Knex** was not tested. Neither was Prisma without `@prisma/adapter-pg` (whether Prisma 7 can run without an adapter).
- **Narrow coverage:**
  - The `nopg`/`nopg-nohoist` workspaces, the F1 crash-direction checks, the F3, F4 and F5 tests, and the Q2 variants ran on current Node (26.13.0) only.
  - The fastify and platform-node adapter checks of `GET /out` also ran on current Node only (the library spans do not depend on the adapter).
- **`pg` de-dup residual:** the `Object.create(config)` alternative is untested.
- **Pool wait time:** the single-rule proposal is not implemented.
- **pnpm with two `pg` versions in the graph and none listed by the app:** which one pnpm links to the optional peer was not tested. Neither was npm's or Yarn's layout.
- **Cost:** the require-in-the-middle hook installed by `UndiciInstrumentation`, and the wrappers' per-call overhead, were not measured. Phase 1 benchmarks answer both.
- **ioredis gaps:** `ioredis:batch` (MULTI) and `ioredis:connect`, mysql2's `connect` channel, and ioredis Cluster were not subscribed or tested. The offline-queue parent loss has no fix without patching ioredis; an upstream change (trace on enqueue) would answer it.
- **Linux:** only darwin-arm64 was run. The CI matrix on Linux would confirm.
- **The CJS dual-package hazard:** no Nestrix-side mitigation is proven (see F5). P0-S3 or P0-S4 owns it.
