## Answers

| # | Question | Result | Evidence |
|---|---|---|---|
| 1 | Metadata on the server, per transport: where does what the dispatch hook injects arrive, and how is it read through public APIs? | **pass** for TCP, Redis, NATS, RabbitMQ, Kafka and MQTT 5; **fail** (by design) for MQTT 3. On all six, `getMetadata()` on the RPC context (the handler's `@Ctx()`, `ExecutionContext.getArgByIndex(1)` in an interceptor or pre-request hook) returns the injected entries for both `send` and `emit`, and a span started from it is parented on the client's span, in the caller's trace. TCP and Redis carry it inside the packet. NATS, RabbitMQ, Kafka and MQTT 5 carry it as message headers, and there `getMetadata()` reads the headers, so it also returns headers the producer set itself: Kafka adds Nest's own `kafka_correlationId`, `kafka_replyTopic`, `kafka_replyPartition` on requests. Kafka header values arrive as strings (Nest decodes them). A header set on the record (`NatsRecordBuilder`, `RmqRecordBuilder`, a Kafka message's `headers`) wins over a metadata entry of the same name. MQTT 3 carries nothing (`getMetadata()` is `undefined`). The processing start hook's context exposes the same `getMetadata()` (TCP run). | `q1-metadata.test.ts`, 7 cases, all pass. | 3 | Client span timing for `send` and `emit`; does the dispatch hook run in the caller's context? | **answered.** `send` is **cold**: nothing is dispatched until subscribed, then once per subscription (two subscriptions, two dispatches). Its span starts at subscription. Ends: a single reply under `firstValueFrom` is `next` then **unsubscribe**, before completion; a streamed reply under `lastValueFrom` is three `next`s then complete; `take(1)` on a stream is next then unsubscribe; a handler error is error; a caller `timeout(50)` is unsubscribe with no value. So "unsubscribed after a value" is a normal end and "unsubscribed before any value" is a cancel. `emit` is **hot**, not cold as the backlog assumed: `ClientProxy.emit` calls `connectable(...).connect()` itself, so the event is dispatched with no subscriber. It returns an rxjs connectable; subscribing to it afterwards does not dispatch again and reports completion, or the error when the server is down. With nobody subscribed, a failed emit raises no `uncaughtException`, with or without an observing subscription. The dispatch hook runs in the caller's async context for both (for `send`, the subscriber's), so a span made active around the call is the one injected; the server span is its child. | `q3-client-timing.test.ts`, 10 tests: `send events ['send:subscribe:b3f9…','send:next','send:end:unsubscribe'] dispatch [{pattern:'sum',activeSpanId:'b3f9…',injected:{traceparent:'00-f0ab…-b3f9…-01'}}]`; spans `['rpc sum','c9f0…','b3f9…']`, `['send sum','b3f9…','6b14…']`; `stream lastValueFrom [1,2,3] [...,'send:end:complete']`; `stream take(1) 1 [...,'send:end:unsubscribe']`; `fail ['send:subscribe:…','send:end:error']`; `timeout ['send:subscribe:…','send:end:unsubscribe']`; `emit events ['emit:call:08c5…','emit:connectable:true','emit:end:complete']` with `dispatch [{pattern:'evt',activeSpanId:'08c5…'}]` and no subscriber; `emit to dead server [...,'emit:end:error'] uncaught 0`; `raw emit to dead server, uncaught 0`. |

Also run (alternative, not chosen): `ModulesContainer.getRpcTargetRegistry()` (public, documented "contains all RPC targets registered in the application") emits each `Server` to a subscription made in a provider constructor (`target:ServerTCP`), and `setOnProcessingStartHook` set from there runs for every message with the RPC context. ## What this changes

- nest-hooks.md §5: metadata per transport (as run); `emit` is hot; the pre-request hook's deferred `next()`; `onDispatchHook` and `onProcessingStartHook` are `protected` in the typings, so another tool's hook cannot be detected through public API; the RPC target registry; the coverage table of Q2. Done in this change.
- architecture.md §4.2: a "Microservices" part (handler spans, client spans, injection, the hybrid line, what is not covered). §4.1's level 1 row already lists microservices. Done in this change.
- backlog phase-4: P4-01 status and the public API (`instrumentClient`, `nestrixPreRequestHook`). Done in this change.
- Decisions affected: D-38 stands (client spans from wrapping `send`/`emit`, the dispatch hook only injects, the hybrid fallback is a pre-request hook with `deferInitialization: true`). One correction to its premise: `emit` is hot, so the PRODUCER span starts at the call, not at subscription. A new decision is proposed for the hybrid mechanism (below); it is the lead's to record.
- P3-03 (trace type): a root SERVER span from a `@MessagePattern` handler would be typed `http` by the rule "root is a server span". It should be `other` (or a new `message` type); the root can be told apart by `messaging.system` / `messaging.operation.type`. Not changed here (P3-03 owns it).

## Chosen approach

The design stands, with D-38's fallback for hybrid apps. Handler spans come from Nestrix's existing global interceptor (an `rpc` branch), which covers microservice-only apps and hybrid microservices connected with `inheritAppConfig: true`; for a default hybrid app the user adds one line, `app.connectMicroservice(options, { deferInitialization: true }).registerPreRequestHook(nestrixPreRequestHook)`, which also covers guard rejections. Both entry points share one function, which extracts from `getMetadata()`, starts SERVER (`@MessagePattern`) or CONSUMER (`@EventPattern`, from the `microservices:handler_type` metadata) named `<transport> <declared pattern>`, subscribes the handler's stream inside the span's context, and ends it at completion, error or unsubscription; a message is traced once when both run. Client spans wrap `send` (span per subscription) and `emit` (span at the call, ended by observing the hot connectable) on instances, found through `ModulesContainer` at `onModuleInit` for DI clients and through `instrumentClient` otherwise; the dispatch hook injects under the outbound rules. The processing-hook route through the RPC target registry was not taken: it would cover default hybrid apps with no user code, but it gives a span without the handler, its kind or its error, and takes another single slot; D-38 already chose the pre-request hook, and reopening that is the owner's call.

Proposed decision (draft for the lead): "**D-64 Hybrid microservice handler spans.** Nestrix's global interceptor gives handler spans in microservice-only apps and in hybrid microservices connected with `inheritAppConfig: true`. A default hybrid app adds `{ deferInitialization: true }` and `.registerPreRequestHook(nestrixPreRequestHook)`. Not taken: processing hooks through `ModulesContainer.getRpcTargetRegistry()` (no handler, kind or error; single slot). Evidence: P4-S1 Q2."

## Left open

- **gRPC**: not run. By the source, `ClientGrpcProxy` applies the dispatch hook per call through `getService()` (so injection should work) but has no `send`/`emit`, so the build sets the hook and wraps nothing; the server's gRPC handler receives a gRPC `Metadata` object, which has no `getMetadata()`, so the build extracts nothing there (a root span). Answered by a gRPC run with `@grpc/grpc-js` and a proto.
- **MQTT 5 options**: only `protocolVersion: 5` on both sides was run. Whether a client on 5 and a server on 3 (or the reverse) loses metadata silently was not run.
- **NATS without header support** (a server older than 2.2): Nest's doc comment says metadata is left off; not run.
- **Kafka `emitBatch`**: the dispatch hook runs per message (by source), so context is injected, but no PRODUCER span is made (only `send`/`emit` are wrapped). Not run.
- **Node 22 and 24**: not run; nothing here is version-specific by the source (rxjs and `AsyncLocalStorage` only).
- **Custom transports** (`strategy`): recognised by no class name, so spans are named `rpc <pattern>` with no `messaging.system`; a custom client whose `emit` is cold gets a PRODUCER span covering the call only (the build does not subscribe to it). Not run.
