# P0-S3 Coexistence

Date 2026-11-11. darwin-arm64. Every test ran on Node 26.13.0 and again on Node 22.15.0 (`S3_NODE=...`): 58 passed, 1 skipped on each, with `S3_Q5_DIR` set. NestJS 12.4.2 with `@nestjs/platform-express`, `platform-fastify` and `platform-node` 12.4.2. OpenTelemetry: `@opentelemetry/api` 1.10.0; `sdk-trace`, `core` and `context-async-hooks` 3.1.1; `instrumentation-undici` 0.35.0. Sentry: `@sentry/nestjs` and `@sentry/core` 11.11.0 (why not 11.12.0 is under "Versions"). For Q5's SDK 2 host: `@opentelemetry/api` 1.9.1, `sdk-trace-base`, `sdk-trace-node`, `core` and `context-async-hooks` 2.12.1. npm 11.20.0, pnpm 12.16.1, Vitest 4.1.12. All versions came from `npm view` on the day. An independent review's findings are folded in below.

`@nestrix/nestjs` is still a placeholder, so Nestrix is played by a stand-in in `spikes/p0-s3/src/nestrix/`. It is plain ESM JavaScript, so a CommonJS host reaches it through `require(esm)`, just as it would reach the real package:

- `instrumentation.mjs`: imports `@opentelemetry/api` only. It contains:
  - the request hook: extract, start the server span, store `{ span, route }` under a context key Nestrix owns, attach a `close` listener, call `done()` inside `context.with`;
  - the route-triggered hook: chained, and it reads only that key;
  - a `node:http` client subscriber that honours OpenTelemetry's suppress-tracing key and requires an active parent.

  The hooks are set from a provider constructor through `HttpAdapterHost`. Every body is guarded, and fault injection is available through `globalThis.__nestrixFault`.
- `setup.mjs`: the only file that touches the SDK. It provides `nestrixSpanProcessor()` (a duck-typed plain object) and `setupNestrix()`.
- `detect.mjs`: probes that use only the public API.

Each scenario runs in its own Node process, because OpenTelemetry and Sentry globals are per process. The Vitest parent sends requests from outside, so the process under test never instruments its own driver. The local Sentry DSN and the downstream server are recorders that run in the test process. Nothing went to sentry.io. The DSN must match `http://pk@127.0.0.1:` or the instrument file throws.

## Inputs from other spikes

- **P0-S2: a tracer obtained before Nestrix registers stays a no-op forever.** Real, but only across the two api copies. `test/early-tracer.test.ts`.
  - **Within one copy**, a tracer obtained before registration records afterwards (`ProxyTracer` looks its delegate up lazily).
  - **Across copies**, a CJS host's module-level tracer stays a no-op after Nestrix registers through `.mjs` (`cjsEarly:false`). Tracers obtained after registration from either copy work.
  - **Cause:** `setGlobalTracerProvider` puts the registering copy's own `ProxyTracerProvider` into the global and sets the delegate on that one only.
  - **Registering through the `.cjs` copy instead** only moves the problem: then `esmEarly:false`.
  - **Level 4:** `@opentelemetry/instrumentation@0.301.1` takes its tracer in the `InstrumentationBase` constructor (`dist/instrumentation.mjs:20`), and `registerInstrumentations` uses that copy's own `getTracerProvider()` (`autoLoader.mjs:11`). "level 4: an upstream instrumentation a CJS host constructs before Nestrix registers loses its spans": `UndiciInstrumentation` from the `.cjs` copy, constructed before Nestrix registers through `.mjs`, exports no client span. The outgoing `traceparent` then names Nestrix's server span, because the no-op tracer passes the parent through. Constructed afterwards, the client span exists and is parented to the server span.
- **P0-S5/S1: an `HttpAdapterHost.init$` subscriber that throws crashes the process via `uncaughtException`.** Not retested. The stand-in subscribes to no Nest observable. It adds to rule 1: any subscription Nestrix makes to a Nest observable needs the same guard as a diagnostics-channel subscriber.

## What this changes

Proposed edits, not applied. The lead applies them after review.

- **architecture.md §4.2, route-triggered hook:**
  - The route hook touches only Nestrix's own server span, found through a context key Nestrix owns, never `trace.getActiveSpan()`, which may be another tool's span (Q4c′).
  - The route is kept in Nestrix's own per-request state as well, because `updateName` on a non-recording span does nothing and the route statistics recorded before sampling (§4.6) must not depend on the span (Q2, `routeStats` under `AlwaysOffSampler`).
- **architecture.md §4.2, "Nestrix's own routes and its exporter's requests are never traced":** replace with three rules:
  1. honour OpenTelemetry's suppress-tracing context key (`createContextKey("OpenTelemetry SDK Context Key SUPPRESS_TRACING")`, API-only; it covers every SDK exporter, because both span processors wrap export in `suppressTracing`: `BatchSpanProcessorBase.mjs:99`, `core/internal/exporter.mjs:10`);
  2. create no client span and inject no header when there is no active parent span (undici: `requireParentforSpans: true`);
  3. a configurable host ignore list, for requests made inside a request on behalf of another tool (Sentry's error envelope, Q4d).
- **architecture.md §4.2, registration timing:** Nestrix registers its globals no earlier than `NestFactory.create` (provider construction or later), never at import or `forRoot()` time. In an ESM `main.ts` that imports `AppModule` and then starts its SDK in the module body, `forRoot()` runs first, and registering there takes every slot from the host (Q1a).
- **architecture.md §4.5, "When the host already has an SDK":**
  - The mechanism holds across module formats, adapters and Node 22.15/26 (Q1).
  - Nestrix probes for a context manager (sync round trip; the async variant only warns) and a propagator (`propagation.fields()`), and registers neither when one exists. The probes are silent; a failed `setGlobal*` writes a stack trace through the host's diag logger.
  - Decide whether the provider check accepts that one diag error.
  - A provider that loses the registration race is shut down, and `shutdown()` reaches its processors, so it must never be built with a processor the host also uses.
  - Nestrix obtains tracers at use time, never at module top level.
  - In a CJS host where Nestrix owns the provider, the host's module-level tracers and **any upstream instrumentation it constructed before Nestrix registered** stay no-ops.
- **architecture.md §4.1, level 4:** add the caveat. In a CommonJS app where Nestrix owns the provider, upstream instrumentations constructed or registered before Nestrix registers produce no spans. The host must construct them after `NestFactory.create`, or own the provider itself.
- **architecture.md §4.5, `nestrixSpanProcessor()`:** duck-typed across copies (confirmed). `onStart` and `onEnd` must catch everything, and `forceFlush` and `shutdown` must never reject (Q2b, Q2c). It sees every recording span.
- **architecture.md §4.5, dependency budget (rule 10, owner):** SDK 3's `TracerProvider` has no `register()` and `sdk-trace` exports no ALS context manager (`StackContextManager` only). When Nestrix owns the provider it needs an ALS context manager and a W3C propagator. Options, neutrally:
  - (a) add `@opentelemetry/context-async-hooks` and `@opentelemetry/core` (core 3.1.1 is already present transitively, pinned exactly by `sdk-trace`);
  - (b) `core` only, plus a first-party ALS context manager;
  - (c) both first-party.
- **architecture.md §4.5, Sentry:** replace "The supported setup is decided in spike 3" with Q4's facts. No setup tested gives one trace with Sentry's defaults and a fully working Nestrix:
  - (a) defaults give two traces and two header families;
  - (b) the documented `openTelemetryIntegration()` setup still gives two, unless `defaultIntegrations: false`, which loses Sentry's base integrations (listed in Q4b) but keeps `SentryGlobalFilter`;
  - (c) `enableOpenTelemetrySetup: true` gives one trace, but Nestrix's context does not survive Sentry's Express instrumentation, its `traceparent` is refused with a stderr line per call, and the store stays empty.
- **research.md §4:**
  - Correct the Sentry row: `@sentry/node` 11.11.0 (not only 11.12) defaults `enableOpenTelemetrySetup` to `false`. The integration is `openTelemetryIntegration()`; `otlpIntegration` does not exist in 11.11.0 or 11.12.0. Its JSDoc says "An active Sentry span still takes precedence". With default integrations a non-recording Sentry span is always active, even without `tracesSampleRate`, so the event and the outgoing `sentry-trace` stay on Sentry's trace. The JSDoc example's `provider.register()` does not exist on SDK 3.

  - Add: Sentry 11 instruments `node:http` and undici through diagnostics channels and injects headers in `http.client.request.created` (relevant to P0-S2 Q2). Its transport does not set OpenTelemetry's suppress key.
  - Add the api 1.x global-version rule, both directions (Q5): the first registration of any kind fixes the version, and a copy of another minor version can neither read nor write it, silently.
  - Add: SDK 3 has no `register()`; hosts register through the API.
  - Add: `InstrumentationBase` takes its tracer at construction.

### For the owner

- **O-1 (SDK 2.x hosts).** Facts:
  - npm refuses the install (`ERESOLVE`) unless the host passes `--legacy-peer-deps` or `--force`.
  - pnpm installs with a one-line warning.

## Chosen approach

For an OpenTelemetry host, the design in architecture.md §4.5 stands: try `setGlobalTracerProvider`; on `false`, stay on the API and ask the host to add the duck-typed `nestrixSpanProcessor()`; probe for a context manager and a propagator and register them only when absent. This works for ESM and CJS hosts on all three adapters on Node 22.15 and 26, with context crossing the dual api copies. Additions:

- Every processor method is guarded, and flush and shutdown never reject.
- Tracers are obtained lazily.
- Registration happens no earlier than `NestFactory.create`.
- A losing provider gets its own processors.
- The route hook touches only Nestrix's own span, through Nestrix's own key, and keeps the route in Nestrix's state.
- The outbound subscriber honours the suppress key, requires a parent, and takes an ignore list.
- The ALS context manager and W3C propagator come from one of the dependency options.

Sentry is not a solved case; see O-2.

## Left open

- **Why Nestrix's context does not survive Sentry's Express instrumentation** (4c). It is inferred from parentage. Reading the orchestrion Express wrapper in `@sentry/server-utils` would confirm it.
