## Detecting shadowing

None of these was chosen; each has a cost that §4.6 should state.

- **Startup self-request (run).** After `HttpAdapterHost.listen$`, one loopback request with a nonce to Nestrix's own probe route; shadowed if the handler did not see the nonce. Agreed with a client's view in all 16 tests that used it. Costs and blind spots, from reading the mechanism (only the agreement was tested): it goes through the host's middleware, so a host auth gate or rate limiter answering 401/429 is misreported as "shadowed"; when shadowed it runs the host's catch-all handler; it shows up in host logs and creates a trace at every startup; it must pass Nestrix's own `ui` gate (it is a loopback request with a loopback `Host`, so `ui: 'auto'` admits it, but a token-protected dashboard needs the probe exempted or authenticated); it never runs when `listen()` is not called (serverless handlers, `init()`-only tests, `inject()`); it needs the listener reachable over loopback (tested only on 127.0.0.1, `::1`, `::`).
- **Passive detection on real traffic (run, the reviewer's proposal).** The request hook marks requests under the base path in an `AsyncLocalStorage`; a chained `setOnRouteTriggered` records a host route firing for a marked request (controller shadowing, with the route's path); a marked request whose response closes without reaching Nestrix's handler is shadowed by something else (adapter-level routes such as serve-static). Hooks installed from `init$`. It reported correctly in all 7 cases on the three adapters, including both serve-static cases, and stayed silent when the dashboard was reachable. Costs: it only reports once someone opens the dashboard; it relies on the request hook, a single slot Nestrix also needs for tracing, and on context propagating from the hook to the handler; a host middleware that rejects the request (401) would also read as "closed without reaching us" (not tested; the response status would tell them apart).
- **Static scan with `DiscoveryService` (not run).** Enumerate controllers and route metadata and match patterns against the base path. Misses routes added through the adapter directly (serve-static's fallback, other libraries' `httpAdapter.get`), needs global prefix, versioning and `RouterModule` composition reimplemented.

## What this changes

### architecture.md §4.6 (Mounting, Assets)

- "On Express a host catch-all route registered earlier can shadow them" → also on platform-node: it groups only contiguous route registrations into one specificity-ordered table, so a `use()` between the host's routes and ours (another module's `onModuleInit`, `@nestjs/serve-static`) puts ours in a later table that loses to an earlier catch-all. Fastify was never affected in these tests.
- "Nestrix detects an unreachable dashboard at startup" → name the mechanism and its costs ("Detecting shadowing" above). There is no route-table introspection in public Nest API.
- "through the adapter's `reply` / `setHeader` / `status` ... no per-adapter branch" → wrong. `httpAdapter.reply(res, buffer)` corrupts binary on Express and `httpAdapter.end()` drops headers on Fastify. Replace with: every handler first takes over the raw response, `reply.hijack()` when the response object has one (Fastify), and writes `res.raw ?? res` directly (`statusCode`, `setHeader`, `end(buffer)`). One duck-typed check, byte-exact with all headers on all three adapters, JSON included.
- Add: an exception thrown or a promise rejected out of a dashboard handler reaches the host's global exception filters and Nest's `ExceptionsHandler` log. Every handler catches everything and answers 500 itself, through the same raw, hijacked, stripped response (rule 1).
- Add: host middleware, `helmet`, `compression` and `useSecurityHeaders()` apply to routes registered in `onModuleInit` on every adapter. The dashboard sets its own `Content-Security-Policy` (and any header it relies on) on every response; a handler's `setHeader` replaces the host's value on all three adapters.

### architecture.md §4.7 (Dashboard security), proposed text

> `ui: 'auto'` serves the dashboard only when `@nestrix/ui` is installed, `NODE_ENV` is `development` or unset, and, per request: the socket peer (`(req.raw ?? req).socket.remoteAddress`) is loopback (`127.0.0.0/8`, `::1`, `::ffff:127.0.0.0/104`); the raw `Host` header is present and names a loopback host; and none of `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`, `Via` is present. These are read from the raw socket and raw headers, never from `req.ip`, `req.hostname` or `httpAdapter.getRequestHostname()`, which follow client-supplied forwarding headers when the host trusts proxies.
>
> **Limit.** These checks cannot tell a local browser from a reverse proxy on the same host that forwards public traffic without adding forwarding headers and with `Host` rewritten to the upstream address, which is nginx's default for `proxy_pass http://127.0.0.1:<port>`. Such a deployment with `NODE_ENV` unset exposes the dashboard. The docs say so where `ui: 'auto'` is introduced, and recommend setting `NODE_ENV` in any deployed environment.
>
> The dashboard's own responses never carry CORS allow headers, whatever the host's CORS configuration: each handler first takes over the raw response (on Fastify, `reply.hijack()`; never `reply.send()`, because `@fastify/cors` can run after the handler with `hook: 'preSerialization'` and re-add them) and removes every `Access-Control-*` header before writing, on success and error paths alike. What Nestrix does not control: preflight (`OPTIONS`) requests for dashboard paths are answered by the host's CORS layer, if it has one, with the host's allow headers. That lets a cross-origin page send the actual request, but not read its response, which carries no `Access-Control-Allow-Origin`. The API also rejects `Sec-Fetch-Site: cross-site`.

The forwarding-header list beyond `Forwarded` and `X-Forwarded-For`, and the "Limit" paragraph, are what the review asked for; the list was tested as a rule in `r2-loopback-async.test.ts`, the limit by a real proxy process there. `X-Forwarded-Proto` is my addition (not in the review's list, untested beyond being part of the rule). Whether `ui: 'auto'` should additionally require a startup token is listed under "Left open" for the owner.

### Decisions affected

- **D-31** ("Dashboard routes are registered in `onModuleInit`") gives as its reason that a constructor runs before `initHttpServer`. Q9 shows that constructor-time registration works on every adapter, so that reason does not hold as stated.   | | `onModuleInit` (D-31) | Constructor via `init$` |

  | Works under `NestFactory` / `@nestjs/testing` | yes / yes | yes / yes |
  | Depends on | documented lifecycle hook | `init$` emitting when the adapter is set, which its JSDoc does not promise |

## Chosen approach

Whatever registration point is used, three corrections to §4.6 are required by the evidence: every handler takes over the raw response first (`reply.hijack()` on Fastify, never `reply.send()`), strips `Access-Control-*`, and writes the raw `ServerResponse` instead of `httpAdapter.reply`; every handler catches everything and answers its own 500 on that same response, since escaped exceptions and rejections reach the host's filters; and the loopback facts are read from the raw socket and raw headers with the extended forwarding-header list. With those, `onModuleInit` registration (D-31) works on all three adapters and under `@nestjs/testing`, with host middleware applying to the dashboard and shadowing possible on Express and platform-node. The registration point itself is the owner's call (table above).

## Left open

- **Owner decision: a startup token for `ui: 'auto'`.** The per-request checks cannot see a same-host proxy that adds no forwarding headers (Q7, R2). A token printed at startup and required by `ui: 'auto'` would close that hole at some cost to the zero-config experience. Not decided here.
- **Owner decision: the registration point** (D-31 table above).
- **Node 22.15**: not run (not installed locally). CI's matrix would answer it.
- **Lowest Nest 12** (12.0.0 Express/Fastify, 12.3 platform-node): not run; everything here is 12.4.2. `useSecurityHeaders()` does not exist before 12.1.
- **Answering the preflight ourselves**: an `OPTIONS` route registered at construction would precede host CORS on Express and platform-node and could answer dashboard preflights without allow headers. Not tried. On Fastify host CORS is an `onRequest` hook and would answer first (from source, not run).
- **Registration in `onApplicationBootstrap`**: not tested.
- **`enableCsrfProtection()`**: not tested; its `SAFE_METHODS` (`GET`, `HEAD`, `OPTIONS`) are always allowed (read in `security/cross-origin-protection.js`, not run).
- **Self-request misreports** (401/429 as shadowed), **passive detector with a rejecting host middleware**, **passive detector under `@nestjs/testing`**: not tested.
- **`HEAD` on dashboard routes** and **HTTP/2**: not tested.
