# P7-S1 On-demand CPU profiling

Run on 2026-11-11, Node 26.13.0 only, darwin-arm64 (Apple M1 Pro, 10 cores). `@nestjs/common`, `core`, `platform-express`, `platform-fastify`, `platform-node`, `testing` 12.4.2; `@opentelemetry/api` 1.10.0, `sdk-trace` and `context-async-hooks` 3.1.1; autocannon 9 as the load generator. Linux, Windows, Node 22/24, and loading the files into Chrome DevTools or speedscope were not run (see "Left open").

Code: `spikes/p7-s1/`. The probes are plain JavaScript, each run as its own Node process, because a CPU profile covers a whole process and code transformed by Vitest has no real file URL:

- `probes/q1-apis.mjs`: the three APIs around an ESM and a CommonJS hot function (`fixtures/hot.mjs`, `fixtures/hot.cjs`).
- `probes/q1-repeat.mjs`: several captures in one process.
- `probes/nest-capture.mjs`: captures in a Nest app (`fixtures/app.mjs`, decorators applied as functions) on each adapter.
- `probes/q2-interference.mjs` with `fixtures/q2-child.mjs`: a debugger attached over `--inspect` and driven through the DevTools protocol (Node's global `WebSocket`), and an in-process `Session` standing in for an APM agent.
- `probes/q2-crosstalk.mjs`, `probes/q4-after.mjs`, `probes/start-cost.mjs`, `probes/bench.mjs`.

`fixtures/validate.mjs` checks a profile's structure: the keys; `samples.length === timeDeltas.length`; every sample and child id is a node; the first node is `(root)`; the deltas fit in the span. It also finds functions in the profile. The tests in `test/` run the probes and assert on their output. `test/q5-q6-context.test.ts` runs in-process through `@nestrix-js/testing`'s `bootApp` on all three adapters.

Rerun: `pnpm --filter spike-p7-s1 test` (27 tests, about 60 s, one file at a time). The benchmark is manual: `pnpm --filter spike-p7-s1 bench` (about 8 minutes). Never run two at once.

## Chosen approach (for P7-02)

`v8.startCpuProfile()`: synchronous, no inspector `Session`, no protocol round-trips, no `Debugger` domain, nothing loaded until a capture. It is equivalent in output and cost to the same-thread `Session`, and simpler. The worker route works too but needs a thread and message round-trips (start took 18 ms against 11 ms in a bare process), for no gain. The package's `engines` is `>=26.13.0`, so the API is always there; a wider range down to 22 would need the `Session` route as a fallback.

```js
// Only when a capture is requested; nothing is imported or created before.
const v8 = process.getBuiltinModule("node:v8");
const handle = v8.startCpuProfile({ sampleInterval: 1, maxBufferSize: Math.ceil(durationMs / 1) + 1000 });
// ... after durationMs, from an unref'ed timer, or on app shutdown:
const json = handle.stop();          // string; ~2-5 ms; undefined if already stopped
// discarding instead (shutdown, error): handle[Symbol.dispose]()
```

- **One capture per process,** enforced by Nestrix, because the API allows several. Use a process-wide slot (`globalThis[Symbol.for("nestrix.profiler")]`), so two copies of the package or two Nestrix apps in one process share it. A second request gets a conflict answer (409) with when the running capture ends. No refusal on `inspector.url()` or on other profilers: Q2 found none disturbed, and refusing would disable the profiler for everyone who develops with `--inspect`.
- **Bounds:** default 30 s, at most 120 s. Set `maxBufferSize` from the duration, so a long capture cannot grow past it. The end timer is `unref()`'ed. `onApplicationShutdown` discards a running capture.
- **The start pause is stated, not hidden.** The endpoint answers after `startCpuProfile` returns, with the measured `startMs`. The UI says before starting that the app pauses briefly. It can estimate the pause from `v8.getHeapCodeStatistics()` (`code_and_metadata_size + bytecode_and_metadata_size`, about 10 ms per MB on this machine). The docs give the numbers from this spike. Stop is a few milliseconds.
- **Normalise once after stop,** off the request path (`setImmediate`): parse; turn numeric `scriptId`s into strings and absolute-path `url`s into `file://` URLs (`pathToFileURL`), so the download matches `node --cpu-prof` output; stringify. Parse took up to 2.2 ms for 120 s here. Keep the last three as strings with their metadata: start time, duration, `startMs`, sample count, bytes. The top-functions table can be computed from the parsed object at the same time or in the browser; P7-02 decides.
- **Every call is guarded** (rule 1): `startCpuProfile` can throw (`ERR_CPU_PROFILE_TOO_MANY`; invalid options throw `ERR_OUT_OF_RANGE` / `ERR_INVALID_ARG_TYPE`), and `stop()` can return `undefined`. A failed capture is reported to the dashboard and logged once, and the slot is freed.
- **Docs and UI:** inlined functions can appear under their caller, more often after the first capture in a process, because V8 keeps their own frames only for code optimised while the capture runs. Times are JavaScript on the main thread only; worker threads are not included; lines are those of the running JavaScript (no source maps).
- **Acceptance check ("hot function at the top"):** run the app in a fresh child process, warm the route, take one capture, and look for the function by name. That is how `nest-capture.mjs` passed every run in this spike. A hot function V8 does not inline would make it stricter. In a shared test process, accept the hot function or its caller.
- **Q6 (later, optional):** mark the selected trace's time window on the flame chart, anchored as in Q6. Not per-request attribution.

Proposed decision (draft for the lead): "**D-69 Profiler API.** On-demand CPU captures use `v8.startCpuProfile()` (`node:v8`), with one capture per process enforced by Nestrix through a process-wide slot. No `inspector.Session`, no `Debugger` domain, no refusal on an open debugger port or other profilers. Output is normalised to `node --cpu-prof`'s form (string `scriptId`, `file://` URLs). Not taken: a same-thread `Session` (same output and cost, more moving parts) and a worker with `connectToMainThread` (a thread for no gain). Evidence: P7-S1."

## Left open

- **Chrome DevTools and speedscope were not run.** That they accept the files is inferred: the fields and types match `node --cpu-prof`'s output once `scriptId` is a string and CJS paths are URLs, and both tools document support for that output. Loading one normalised file into each would answer it.
- **Why V8 loses inlined frames for code optimised outside a capture** is not known. The behaviour is measured (10-run counts above) and the mechanism is not. `ProfilingScope` (V8 `cpu-profiler.cc`) logs existing code at start, which is where the information would come from. A V8 issue search, or a run with `--no-turbo-inlining` in a throwaway process, would narrow it. Nestrix must not set V8 flags in a host.
- **The first-capture burst:** the first capture in a process starts with about 100 samples some 20 µs apart (later captures do not). It is harmless (it adds to "(program)" and the first function) but unexplained.
- **Linux and Windows:** sampling uses signals on Linux and a different mechanism on Windows; the effective interval (1.5 ms here for 1 ms) and the start pause will differ. Not run.
- **Large apps:** the start pause was measured against code size in a bare process (TypeScript loaded) and in a minimal Nest app, not in a large Nest app. Answered by running `start-cost`'s measurement inside a big example app.
- **Throughput below about 5%** is not resolved by this benchmark, and latency below 1 ms is not visible in autocannon's figures. A longer interleaved run, with more repetitions, would tighten it. That belongs to the optimisation pass (delivery mode).
