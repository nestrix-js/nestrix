Two strategies were compared throughout:

- **own**: each wrapped method is defined on the instance as a non-enumerable own property (`writable`, `configurable`, like a class method).
- **proto**: the instance's prototype is swapped (`Object.setPrototypeOf`) to a per-class derived prototype holding the wrappers.

Both return the same instance object they were given. Neither uses `Proxy`.

What the table shows, beyond the docs:

- **Value providers pass through.** `addCustomValue` in `core/injector/module.js:261` applies the decorator. Checked by identity: `{ provide: "V", useValue: marker }` reaches the decorator (test "value providers pass through ..."). nest-hooks.md §4 says they do not.
- **Module class instances pass through** (`AppModule`, `ConfigModule`, `TypeOrmCoreModule`, `InternalCoreModule`...). They carry no watermark.
- **The same object can be passed more than once.** `useExisting` passes the existing instance again: `UsersService`, `ConfigService` and `Reflector` were each seen twice by identity. The decorator must be idempotent. Both strategies are: the test "decorating the same instance twice wraps once" passes, including with a second, independent decorator.
- **Function middleware given to `consumer.apply(fn)`** arrives as an instance of a class Nest generates (`core/middleware/utils.js` `mapToClass`), named with a random 21-character id, whose `use` is an arrow-function class field (an own property). `app.use(fn)` passes the function itself.
- **Factory results pass whatever they are**: a Drizzle database (`BaseSQLiteDatabase`), a `ClientTCP`, a plain object, a function, the number 42. A class built by a factory (`FactoryMadeService`) keeps its `@Injectable` watermark.
- **Filters carry `@Catch`, not `@Injectable`.** Guards may carry neither (`UndecoratedGuard`, `UserConstructedGuard`). `Reflector`, `HttpAdapterHost`, `ModulesContainer` carry no watermark; `ConfigService`, `DiscoveryService`, `ParseIntPipe` and the schedule internals do.
- **Request-scoped instances**: once per request. **Transient**: once per injection site (2 here).
- **`@nestjs/testing`**: `TestingModuleBuilder.compile()` accepts only `snapshot` and `preview` (`testing-module.builder.d.ts:34`), and its `TestingInjector` is built without `instanceDecorator`. Passing `instrument` to `createNestApplication(adapter, { instrument })` reaches only what the application's own injector creates later: request-scoped instances, class and function middleware (created during `app.init()`), `useGlobal*()` arguments and `app.use()` functions. **No static controller or service is ever decorated under `@nestjs/testing`.** Test: "@nestjs/testing: compile() takes no instrument option ...". Passing `{ instrument }` as `createTestingModule`'s untyped second argument decorates only value providers and transients from `ModuleRef.resolve` (test "review 10"); see "Left open".
- **`createApplicationContext`** takes `instrument` and decorates as `NestFactory.create` does (Q4 and Q5 run on it).
- The undecorated `instance` Nest keeps for a request-scoped controller (used for route discovery) is not passed to the decorator. Only the per-request instances are.

Findings:

- **A wrapper without the metadata fails open.** On **own**, method-level guards stop applying on static and request-scoped controllers: `GET /users/guarded` returns 200 instead of 403, on all adapters. On **proto**, static routes vanish (404: route paths are read from the derived prototype's wrapper), but request-scoped controllers fail open the same way, because their routes are discovered from the undecorated instance.
- **`name` matters.** Without it, `context.getHandler().name` is the wrapper's own name. `@nestjs/throttler` 6.7.1 builds its storage key as `` `${context.getClass().name}-${context.getHandler().name}-${name}` `` (`dist/throttler.guard.js:166` in the published tarball; read, not run), so every wrapped handler of a controller would share one rate-limit bucket. Copying `name` fixes it.
- **Not needed by any tested feature:** `length` (the "metadata+name" row equals the baseline on all adapters), and other own properties of the function. Parameter decorators (`ROUTE_ARGS_METADATA` is stored on the class under the method name) and pipe metatypes (`design:paramtypes` stored on the prototype under the method name) keep working without copying anything, because Nest reads them from the class and the prototype chain, not from the function. Copying `length` and own properties costs nothing per call, so the recommendation is to keep D-34's full list. **Minimal set: every own reflect-metadata key, plus `name`.**
- Copying is a snapshot taken at decoration time. Metadata added to the original function after the instance is created would not reach the wrapper. Nothing in Nest or the tested libraries does that; it is a residual risk, not an observed failure.
- **proto changes route order on Express.** Nest registers routes in `MetadataScanner.getAllMethodNames(Object.getPrototypeOf(instance))` order (`core/router/paths-explorer.js:12`). Under **proto**, wrapped methods live on the derived prototype and are listed first; any method left unwrapped (excluded by the user, a generator, a failed metadata copy) moves after them. In the fixture, excluding `guarded` from wrapping made `GET /users/guarded` match `@Get(":id")` first and answer **400** from `ParseIntPipe` instead of 403 (`Q2 route order`, Express/proto). Fastify and platform-node match by specificity and were unaffected. **own** leaves the prototype, and therefore the route table, untouched. This decides the strategy: **own**.
- Spans nest correctly: `UsersController.findAsync` is the parent of `UsersService.findAsync`, which is the parent of `UsersService.find`, and the async span covers the awaited timer.
- Wrapping every class instance (rule "everything") still served `GET /users/db` correctly through TypeORM, Drizzle and the raw `DataSource.query`. Correct, but noisy (Q7).

### Q3: where Nest gets the handler

- **Static controllers**: `PathsExplorer.exploreMethodMetadata` (`core/router/paths-explorer.js:22-23`) reads the route path and method metadata from `prototype[methodName]`, where `prototype = Object.getPrototypeOf(instance)`, and keeps `instance[methodName]` as the callback. Guards, interceptors, pipes, filters, `@HttpCode` and `@Header` are then read from that callback once, at route registration.
- **Request-scoped controllers**: `createRequestScopedHandler` (`core/router/router-explorer.js:263`) resolves a new instance per request and calls `createCallbackProxy(contextInstance, contextInstance[methodName], ...)`, so the handler and its metadata are read **from each request's instance, on every request**.
- Run: a global guard recorded `context.getHandler()` for a static route, a request-scoped route (twice) and an explicitly request-scoped route. It was our wrapper every time, on all adapters and both strategies. Under **own** the class prototype is untouched (`isWrapper(UsersController.prototype.code) === false`), so the call can only have come from the instance.
- The same holds outside HTTP. `@nestjs/schedule` reads `instance[key]` and its metadata (`schedule.explorer.js:60`), and `@nestjs/bullmq` binds `instance.process` (`bull.explorer.js:134`, `:129` for request-scoped processors).

All under both strategies, through `createApplicationContext`:

| Case | Result |
|---|---|

### Q5: schedule and BullMQ

- `@Interval("s6-tick", 20)` and `@Cron(EVERY_SECOND)` ran the wrapped method: 61-62 interval runs and as many `TickService.tick` spans in 1.3 s; cron runs equal cron spans in every run (1 or 2, depending on how many whole-second boundaries the window spans).
- With a wrapper that lacks the metadata, the schedule explorer finds no metadata on `instance[key]`, and the job is **silently never scheduled** (0 runs). This is another fail-silent case covered by copying metadata.
- BullMQ against Redis 8: with the processor selected, `S6Processor.process` and the `@OnWorkerEvent("completed")` handler both produced spans, and the job completed. `@Processor` only sets `SCOPE_OPTIONS_METADATA` and `bullmq:processor_metadata` on the class (`@nestjs/bullmq/dist/decorators/processor.decorator.js`), not `@Injectable`, so a rule keyed on Nest's watermarks does not wrap processors (no span, job still processed).
- `bullmq` 6 makes `ioredis` an optional peer. Given connection options and no `ioredis`, BullMQ fails at queue creation ("could not load the optional 'ioredis' package"). The spike passes a connected node-redis client (`redis` 6.3.1) as `connection`, which BullMQ 6 adapts.

The first run (before the review fixes) measured 10-40 ns less per call on api-noop (138 / 157 / 187 ns for 1 / 10 / 100 methods). The difference is the call-time prototype lookup added for review item 4; at 100 methods that lookup site sees 100 prototypes.

**Fast path inside an unsampled parent** (sdk-unsampled, inside an active parent span whose context has no SAMPLED flag, 10 methods, own): **666.2 (660.7-768.1) ns off, 95.1 (92.4-99.7) ns on**, against a 23 ns raw call. Inside a sampled parent (sdk-recording) the check costs about 20 ns (999.2 vs 1017.9 ns) and never skips. The skip condition is: the active span context is valid and its `traceFlags` lack `TraceFlags.SAMPLED`. The first version of the fast path keyed on `span.isRecording()`. That is wrong: in SDK 3.1.1 `isRecording()` is `this._ended === false` (`@opentelemetry/sdk-trace/dist/Span.mjs:202`), so after a sampled request span has ended, fire-and-forget work lost its spans. Review test "review 1": fast path on and off now both give `["GET /orders","Mailer.send"]`; the old condition gave `["GET /orders"]` with it on. Validity is checked against the all-zero ids rather than with `isSpanContextValid`, whose hex regexes cost about 60 ns per call here (155 ns with them). Under SDK 3's default sampler, `ParentBased(AlwaysOn)` (`@opentelemetry/sdk-trace/dist/TracerProvider.mjs:24`), a child of an unsampled parent is not sampled either. So with that sampler the fast path changes cost, not what is recorded (test "Q6 fast path ..."). Under a sampler that is not parent-based it would change what is recorded, and the fast path should be tied to the sampler choice.

Per-instance detail (`node bench/install-variants.ts`, ns per `new` plus install, median of 7): `defineProperty` loop 118 / 1215 / 16163 for 1 / 10 / 100 methods; `defineProperties` with a cached map is slower (237 / 1568 / 20427); `setPrototypeOf` is flat at about 100. Plain assignment is fast (25 / 142 / 3059) but makes the methods enumerable, which changes `Object.keys` and `JSON.stringify`, so it is not acceptable.

What it means:
- **Per call**: the cost is dominated by the OpenTelemetry SDK and the AsyncLocalStorage context switch, not by the wrapper (api-noop: 150-220 ns).
- **Per instance, own**: about 150 ns per wrapped method at 10 methods and about 200 ns at 100, from `new` + decorate minus `new` alone. Singletons pay it once; request-scoped and transient classes pay it on every creation.
- **Plan building**: once per class, 0.08-0.36 ms in single samples, including JIT warm-up.

Per-request spans under "markers": `GlobalGuard.canActivate`, `ClassMiddleware.use`, `GlobalInterceptor.intercept`, `RecordingInterceptor.intercept`, `GlobalPipe.transform`, `ParseIntPipe.isNumeric`, `ParseIntPipe.transform`, `TransientService.which`, `ConfigService.getFromInternalConfig`, `ConfigService.get`, `UsersService.find`, `UsersService.findAsync`, `UsersController.findAsync`. Under "everything", one DB request produced 54 spans, 40 of them `DataSource.*` calls (`findMetadata`, `getMetadata`, `createQueryRunner` and similar).

**A conflict the owner has to resolve first.** Both options below leave guards, pipes, interceptors and filters unwrapped, but architecture.md promises spans for them at level 2:
- the §2 table says "guard and filter level with level 2" (exception monitoring) and lists "Provider, guard, pipe, interceptor spans";
- the §4.1 level table lists "Spans for provider methods, guards, pipes, interceptors and filters";
- §4.2 says "Exceptions thrown by guards are captured at level 2".

So either the owner amends §2, §4.1 and §4.2 to drop enhancer spans, or the default keeps enhancer spans. Keeping them would at least mean a guard's `canActivate` and a filter's `catch` (meaningful durations and exceptions), with interceptor spans needing an Observable-aware wrapper that does not exist yet (review item 7). The spike measured the noise enhancers add ("markers" row: 7 of 13 spans per request are enhancer or framework spans), not their value.

**Two options, presented neutrally.** Both need the same method selection and the same root policy; in particular both rely on entry methods starting real root spans (review item 2).

- **Shared method selection**: string-named prototype methods from the class up to `Object.prototype`. The walk stops at built-in prototypes and at `EventEmitter.prototype`. Skipped: accessors, generator and async-generator functions, `constructor`, lifecycle hooks, `toString` / `toJSON` / `valueOf`, symbol keys, and names shadowed by an own property.
- **Shared root policy**: a method span starts only under an active span, never as a new root. The exceptions are entry methods: methods with `@nestjs/schedule` metadata (`SCHEDULER_TYPE`), BullMQ `process` and `@OnWorkerEvent` handlers. An entry method starts a new root span (`{ root: true }`) with a link to the span active at call time, if any, plus the SAMPLED-flag fast path.

**Option A, broad.** Classes selected (evaluated once per prototype):
- `@Controller` classes;
- `@Injectable` classes whose duck-typed role is a plain provider: no `canActivate`, `intercept`, `transform`, `catch` or three-argument `use` on the prototype chain, read from descriptors;
- BullMQ processors (`bullmq:processor_metadata` on the class, or a `WorkerHost` instance);
- minus a built-in denylist of framework classes matched by identity (`ConfigService`, `DiscoveryService`, `ModuleRef`, `Reflector`, `SchedulerRegistry`, `ScheduleExplorer`...);
- then user `include` / `exclude`.

Shows services out of the box. Weakness: the denylist is incomplete by construction. Unexported framework classes (`SchedulerMetadataAccessor`, `SchedulerOrchestrator`: 570 root spans without the root policy) and any third-party `@Injectable` service called during a request (a JWT service, an HTTP client wrapper, a logger) get spans unless listed or excluded.

**Option B, narrow.** Classes selected: controllers, BullMQ processors, and classes that have at least one scheduled method; services only when the user opts in through `include` or a Nestrix class decorator. Weakness: shows less out of the box (no service spans by default). No third-party or framework noise by construction, and no denylist to maintain.

Rejected by the evidence: "everything" wraps module instances, Nest internals and ORM objects, and multiplies span count 27x on a DB request (54 against 2). "markers" wraps framework services and enhancers, and misses processors.

## Chosen approach

Wrap through `instrument.instanceDecorator` as architecture.md §4.3 says; the mechanism works on all three adapters and through `createApplicationContext`. Use the **own** strategy:

- install each wrapper as a non-enumerable own property of the instance;
- cache one wrapper per class and method;
- copy every own reflect-metadata key, `name`, `length` and own properties, and install nothing for a method whose copy failed;
- resolve the method on the class prototype at call time;
- return the same instance, idempotently;
- follow only plain native promises, via a derived `then`, and leave subclasses, other thenables and Observables alone;
- skip accessors, generators, lifecycle hooks and own-property names;
- short-circuit under an unsampled parent context;
- start entry methods as linked roots.

Every wrapper and decorator body catches its own faults. `test/faults.test.ts` injects a throwing `startSpan`, `end`, `setStatus`, context manager (before and after the call), error reporter, `then`, class rule and `Reflect.defineMetadata`; in each case the host sees unwrapped behaviour and the guard still applies. The call-time lookup is inside the same protection: a lookup that throws falls back to the captured method. The design in architecture.md stands, with the additions listed above. The default selection rule, and whether enhancers get spans, are O-3's to decide.

## Left open

- **`@nestjs/testing`**: static instances are never decorated, so method spans are absent in apps tested through `Test.createTestingModule`. Known so far:
  - **run**: `compile()` takes no `instrument` option; `createNestApplication(adapter, { instrument })` decorates request-scoped instances, middleware, `useGlobal*()` arguments and `app.use()` functions only (Q1 test).
  - **run**: passing `{ instrument }` as `createTestingModule`'s untyped second argument decorates only value providers at compile time and transients created by `ModuleRef.resolve`. `ModuleRef.create` did not reach it, and static class providers were never decorated. The published type excludes that argument, so this is not a fix (test "review 10": `atCompile: ["Svc"]` is the value provider instance, `afterCreateAndResolve: ["Tr"]`).
  - **source-read, not run**: decorating already-created instances in place through `ModulesContainer` would have to happen before `registerRouter`. `nest-application.js:128-130` runs `registerModules()` → `registerRouter()` → `callInitHook()`, so an `onModuleInit` pass is too late for static routes, whose handlers are captured at registration (Q3). A `configure(consumer)` pass runs inside `registerModules()` (`middleware-module.js:58`) and is early enough, but only in HTTP applications and only if Nestrix's module is a `NestModule`.
