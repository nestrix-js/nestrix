### Reading the response at `close` (Q4)

`q4-close`, all three adapters:

- **Completed responses** (`/hello` 200, unknown route 404, `/private` 403, `/boom` 500, `/teapot` 418, `/stream` 200 with all four chunks): exactly one `close` each, with `headersSent`, `writableEnded` and `writableFinished` all true and the right `statusCode`. The listener runs **inside** the request's store.
- **Client aborts**: the socket is destroyed after `chunk 1` of `/stream`, 50 ms into `/stream` before any byte, or 50 ms into a 300 ms handler while it is still running. Exactly one `close` each, with `writableEnded: false` and `writableFinished: false`. `headersSent` is true for the mid-stream abort and false for the other two. `statusCode` is **200 on all three, even where nothing was sent**. The listener runs **outside** the request's store.
- **App finished, delivery cut**: a handler returns 201 with a 16 MiB body in one call, and the client leaves after the first bytes. `statusCode: 201`, `headersSent: true`, `writableEnded: true`, `writableFinished: false`. This matches the reviewer's plain `node:http` check with 64 MB. So `writableFinished: false` means "not fully delivered", not "client aborted". **Node 22.x and 24 before 24.20 report `writableFinished: true` here** (found by CI on 22.15.0); see docs/research.md, "Delivery cut, `writableFinished` and Node versions". The figures above were taken on Node 26.

The rule that follows:

- `headersSent` true: `statusCode` is what was sent.
- `writableEnded && !writableFinished`: the app finished the response; its delivery was cut.
- `!headersSent && !writableFinished`: no response was sent; record no status.

Because the listener runs outside the store on aborts, the span must be held by the listener's own closure, never looked up from the active context.

### Requests that never reach the hook (Q6)

`q6-malformed`, using raw `net` sockets:

- **Every adapter (Node's HTTP parser answers first):** invalid header name → 400; headers over 16 KiB → 431; request target without a leading slash → 400.
- **Fastify only:**
  - `/users/%zz`, `/users/%` and `/users/%FF` → 400, without the hook.
  - A 150-character parameter → 414, without the hook (default `maxParamLength` is 100).
- **Express runs the hook for all of these:** the three bad escapes give 400, the long parameter gives a 200, and `/hello#frag` gives a 200.
- **platform-node also runs the hook for all of these:** 400, 400, 400, 414, and 400 for the fragment, answered after the hook.
- **Host-supplied server instance** ("Q6 host-supplied server instance with its own early layer"): an `express()` app with its own middleware passed to `new ExpressAdapter(server)`, or a Fastify instance with its own `onRequest` hook passed to `new FastifyAdapter(instance)`. The host's layer runs **before** the request hook and sees no store. When it answers (429 for `/early`), the hook never runs. platform-node was not tried.
- **Inferred, not run:**
  - Requests Node ends on `requestTimeout` / `headersTimeout` before the request is dispatched.
  - `upgrade` and `CONNECT` requests, which Node emits as separate server events.
  - `Expect: 100-continue` when the host installs a `checkContinue` listener.

Every request that reached the hook also got its `close`. Seen once ad hoc and not kept as a test: a client that sends a request and disconnects within about 1 ms sometimes never reaches the hook. In 15 attempts, no request reached the hook without also getting `close`.

### The `init$` subscription (Q7, Q8)

Two conditions make the fallback work. Both were checked:

- **Its body must catch everything.** A subscriber that throws is not reported to the code that set the adapter: rxjs rethrows the error on a timer as an `uncaughtException`, and the setter returns normally. The child-process test "Q7 an init$ subscriber that throws, unwrapped" shows it: exit status 1, stdout `setter returned normally`, the error thrown from `rxjs/…/reportUnhandledError.js`, and nothing printed after it. In a host application that kills the process. The spike's subscriber now wraps its whole body. "testing module: a fault inside the wrapped init$ subscriber…" injects a throw after installing; the app starts and both hooks work.
- **It depends on when `init$` emits.** It emits when the adapter is **set**: the `HttpAdapterHost` setter calls `_init$.next()`, and `@nestjs/testing` calls `container.setHttpAdapter()` at the start of `createNestApplication()` (`testing-module.js`). The JSDoc says the event fires "when the HTTP application is initialized", which is later. If Nest moves the emission to match its JSDoc, the route hook would be set after routes are registered and would silently stop firing under `@nestjs/testing`. Phase 1 should have a regression test that asserts `http.route` on a span from an app built with `@nestjs/testing`, run by the nightly latest-12.x job.

### Version boundaries (from the published source)

Read in the tarballs of every 12.x release (`npm pack`, then grep):

- `runRequestHook` (Express) and `runLifecycleHook` (Fastify) add the `try`, the once-guard on `done` and the promise handling. They first appear in **12.1.3**; 12.0.0 to 12.1.2 call the hook bare. Run: 12.0.0, 12.3.0 and 12.4.2.
- platform-node's `bindAsyncScope` in `body-parser/body-parser.js` first appears in **12.3.2**. Run: 12.3.0 (store lost) and 12.3.2 (store kept). 12.3.1: source only.
- Inferred from the 12.0.0 source, not run: a request hook that returns a rejected promise is an unhandled rejection there. Express calls the hook with `void`, and Fastify ignores its return value.
- Every `@nestjs/*` 12.0.0 manifest declares its Nest peers as `^11.0.0`. pnpm reports unmet peers but links the 12.0.0 copies (checked with `pnpm peers check` and the `.pnpm` links).

## What this changes

Proposals only. architecture.md, nest-hooks.md, research.md and decisions.md were not edited.

**nest-hooks.md §1**
- `@nestjs/testing` bullet: confirmed on 12.4.2 and 12.0.0 that the adapter is `undefined` at construction. Add: `HttpAdapterHost.init$` emits when the adapter is set, which under `@nestjs/testing` is the start of `createNestApplication()`, before `app.init()`. Hooks set from an `init$` subscription made in the constructor therefore work, `setOnRouteTriggered` included. Add the two conditions from "The `init$` subscription" above. Remove "**spike**".
- No-HTTP bullet: replace "`HttpAdapterHost.httpAdapter` is undefined" with "**null or undefined**, and `init$` may never emit". It is `null` under `NestFactory.createMicroservice` and `createApplicationContext`, where `init$` emits `null`. It is `undefined` under `@nestjs/testing`'s `createNestMicroservice()` and for a compiled module never turned into an app, where `init$` never emits. Code must test truthiness and must not wait on `init$`.

**nest-hooks.md §2, request hook table**
- "How the request continues": Fastify continues on a resolved promise only from 12.1.3. Before that, every adapter needs `done()`.
- "If the hook throws": correct from 12.1.3. A throw before `done()` becomes `done(err)`, once. A throw after `done()` is logged on Express and platform-node and dropped on Fastify. Before 12.1.3 there is no guard: a throw before `done()` still gives a 500, a throw after `done()` also gives a 500 although the handler ran, and a rejected promise is unhandled.
- "Requests that skip it", becoming:
  - Fastify: malformed percent-encoding (400), and a parameter longer than `maxParamLength`, default 100 (414).
  - All adapters: whatever Node's HTTP parser rejects (bad header name 400, headers over 16 KiB 431, a target without a leading slash 400).
  - Express and Fastify: whatever a host-supplied server instance does in its own middleware or `onRequest` hooks before Nest's. Such a layer also runs outside the store.
  - Inferred, not run: Node's `requestTimeout` / `headersTimeout`, `upgrade` and `CONNECT`, and `Expect: 100-continue` with a `checkContinue` listener.
  - Express and platform-node run the hook for malformed percent-encoding and long parameters.
- "Whether the context survives body parsing on each adapter is a spike" becomes: it does on Express and Fastify (12.0.0 and later), and on platform-node from 12.3.2, including bodies that arrive in later packets. platform-node 12.3.0 loses it, and so does 12.3.1 by its source.

**nest-hooks.md §2, route-triggered hook**
- Composition (resolves the **spike**): prefix, then `/v<version>` under URI versioning, then the controller path and the method path, with a leading slash and parameters as declared. Header versioning puts no version in the path.
- Replace "Can fire for a route whose host or version filter then declines; treat the last value as authoritative" with: it wraps the version and host filters, so it fires before any of them can decline. Under header versioning on Express and platform-node it fires once per handler tried, and still fires when a request ends in a 404 because no version matched. A declining handler has the same path as the one that accepts, so the last value is right whenever some handler accepts. On Fastify it fires only for the route that matched.
- Confirmed: fires before guards, including for a guard-rejected route; the store is readable inside it.

**nest-hooks.md §2, response close**
- Confirmed on all three adapters. Replace any "abort" wording with the three-line rule in "Reading the response at `close`". Add that the listener runs outside the request's async context when the client goes away.

**architecture.md §4.2**
- The "(spike)" bullet ("If no adapter is available at construction … takes the route template from a global interceptor instead"): the evidence supports a simpler fallback. Subscribe to `HttpAdapterHost.init$` in the constructor when the adapter is not there, with the subscriber's entire body catching everything. Under `@nestjs/testing` both hooks work from that callback. In apps without HTTP it emits `null` or never emits, and nothing is installed. The global-interceptor fallback for the route template is then not needed under `@nestjs/testing`. Whether to adopt it is the lead's call. It depends on the emission timing above, hence the proposed nightly regression test.
- "Route template from `setOnRouteTriggered`": add a rule for a 404 that no version accepted. Proposed, as a design inference that was not run: if the final status is 404 and Nestrix's global interceptor never ran for the request, drop `http.route`. A guard rejection keeps its name, because the guard's route was the one that accepted. The one case that loses its name is a guard that itself throws a 404. Neither level 2 nor a global guard is needed for this.
- "The span ends on the raw response's `close` event": stands. The status comes from the three-line rule, not from `statusCode` alone.

**research.md §1**
- `@nestjs/platform-node`: 12.3.0 is the first release; context across its body parsers needs 12.3.2 (run).

## Chosen approach

The design in architecture.md §4.2 stands, with four amendments.

What holds: a synchronous request hook that calls `done()` once inside `AsyncLocalStorage.run()` gives the store to every guard, interceptor, pipe, handler and request-scoped provider. It survives JSON, multipart and multer body parsing and every `await`, on Express, Fastify and platform-node 12.4.2, and under 50 concurrent requests. `setOnRouteTriggered` gives the composed route template before guards, with the store readable. A `close` listener on the raw response fires exactly once for every outcome.

Set both hooks from the constructor when `HttpAdapterHost.httpAdapter` is truthy. Otherwise set them from an `HttpAdapterHost.init$` subscription made in the constructor, whose whole body catches everything. That covers `@nestjs/testing` and installs nothing where there is no HTTP adapter.

The amendments:

1. Drop `http.route` on a 404 for which Nestrix's interceptor never ran.
2. Read the status at `close` with the three-line rule.
3. platform-node's floor is 12.3.2.
4. Pin the `init$` emission timing with a nightly regression test.

## Left open

- **The 404 route rule** above is a design inference. Phase 1 should test it on all three adapters with header, media-type and custom versioning, and with a host filter.
- **Node 22.15** was not run. It was approximated with Node 24.22.1 and 26.13.0 under `--no-async-context-frame` (all 92 tests pass). Running the suite on Node 22.15, for example in CI's Node matrix, would answer it.
- **12.1.3 to 12.2.x and 12.3.1** were read in source, not run. An alias package pinned to 12.1.3 would confirm the guarded runners.
- **Fastify 12.0.0 with header versioning** cannot start with two versions of one route, so 3b is unanswered there. Whether a later 12.0.x or 12.1.x fixes it was not checked.
- **Requests answered before the hook** produce no span: Fastify's malformed URLs and long parameters, a host's own early middleware, and Node's own parser and timeout errors. Whether Nestrix should see them another way (Node's `http.server.request.start` channel, or Fastify's `frameworkErrors`) was not explored. The timeout, `upgrade`/`CONNECT` and `100-continue` cases are inferred.
- **platform-node with a host-built `NodeRouter`** carrying its own early middleware was not tried.
- Not covered: HTTP/2 and HTTPS servers, `VERSION_NEUTRAL`, a handler with several paths, wildcard routes, and the OpenTelemetry context manager in place of a raw `AsyncLocalStorage`. The context manager uses one underneath, and P0-S3 covers it.
